post-type spec

Repost

Planned · Phase 3a · singular repost / plural reposts · derived from the Phase 3 plan 22 May 2026

A Repost is a short post that amplifies something another person published — a direct share with no added commentary required. The IndieWeb's canonical "repost" verb: u-repost-of points at the original, and the post may carry an optional note in the body. One of five light response types added in Phase 3a.

1. Singular / plural identity

Repost is asymmetric: the type is singular, the URL namespace is plural. The Eleventy collection will be named with the singular (collections.repost), but the folder, URL, and archive will all use the plural.

2. Naming & aliases

JEDEE's amplification type is named Repost (singular) / Reposts (plural), following the IndieWeb repost vocabulary directly. The name is chosen for clarity: a Repost is a deliberate re-sharing of another person's content — not a quote-tweet with commentary (that would be a Reply), not a bookmark for later (that would be a Bookmark).

TermStatusWhere it appears / why
repost / repostschosen nameType, layout, collection, URL, archive (see §1). No feed; not in nav.
repostIndieWeb verb — maps directlyThe µf2 property is u-repost-of. Unlike Jam (which adopts "listen" vocabulary under a different name), Repost uses the IndieWeb verb verbatim.

Slug derives from the filename via | slugify. Repost is a title-optional type (plan Decision 9) — the filename typically reflects the reposted URL or a short description; the slug is never derived from a required title.

4. Frontmatter (planned)

The shape below is the planned authoring surface for a Repost post. No live samples exist yet — this documents the intended structure, not emitted code.

---
repostOf: https://example.com/the-original-post   # required — u-repost-of target
title: ""                                          # optional — falls back to slug
date: 2026-06-01T10:00:00+02:00                    # required — post timestamp
draft: true                                        # optional — shows draft badge
description: ""                                    # optional — card excerpt
tags: []                                           # optional — topic tags (not the category)
---
FieldReq?Role
repostOfrequired for µf2The reposted URL → rendered as the visible u-repost-of anchor (see §5). camelCase is locked (see note).
titleoptionalHeadline; falls back to slug. Repost is a title-optional type — a Repost without a title is valid.
daterequiredPost timestamp (sort + dt-published).
draftoptionalWhen true, the card shows a "draft" badge; post is still built.
descriptionoptionalCard excerpt rendered by card-response.njk.
tagsoptionalTopic tags. Not the category.

camelCase field name — LOCKED. The URL field is repostOf, not repost-of. Nunjucks parses hyphenated top-level keys as subtraction expressions; camelCase is the locked convention across all five Phase 3a light types. The IndieWeb semantics live in the µf2 class on the rendered anchor (u-repost-of), not in the frontmatter key name. See plan Decision: "URL field naming — camelCase (locked)."

category, layout, and permalink will not be authored per-post — they will come from the folder data file src/posts/reposts/reposts.json (see §1 and §12). The folder data file will also set tags: "posts" so reposts appear in the global posts collection; this is separate from per-post topic tags.

5. Microformats (µf2)

The layout WILL emit a visible verb + anchor. The plan specifies the following body block for src/_layouts/repost.njk:

<p>Reposted <a class="u-repost-of" href="{{ repostOf }}">{{ repostOf }}</a></p>
<div class="e-content">{{ content | safe }}</div>
PropertyClassFrom
Repost targetu-repost-ofrepostOf — on a visible <a>
Bodye-contentpost content (optional note)
Publisheddt-publisheddate (via entry-header → date.njk)
Authorshiph-entry / h-card / u-authorhidden block, meta.author

Visible anchor, not hidden <data>. Unlike Jam (which uses <data hidden class="u-listen-of"> because the body provides a separate content area), Repost posts may have no body — the reposted URL is the content. The µf2 target therefore MUST be a visible <a>. This is the plan's locked decision: "Light types render a visible verb + anchor."

h-entry nesting caveat — DEFERRED. Cloning note.njk places the only h-entry in the hidden authorship block; the visible u-repost-of anchor and .e-content will sit outside it, so a strict mf2 parser won't tie the repost property to the h-entry. Accepted for v1 because webmention sending isn't wired up yet. The plan flags this explicitly: "µf2 h-entry nesting — DEFERRED + documented (v1)." Fix deferred to the webmention milestone.

6. Card

Repost WILL use the shared card-response.njk partial — a single card designed for all five Phase 3a light types. It is planned, not yet built.

SlotContent
verb + target"Reposted" + link to repostOf URL
datedate + a "draft" badge when draft: true
contentdescription excerpt, if present

The plan specifies: card-response.njk is modeled on card-notes.njk but drops the title/headline assumption (these types are often title-less). Renders a <custom-card> WebC component (no image slot); styles via css/custom-card.css.

Repost shares this card with Bookmark, Like, Reply, and RSVP. A dedicated card-repost.njk is not planned — the shared card is the design decision for all five light types.

8. Feed

Repost has no dedicated feed. This is a deliberate design decision, not an omission.

The plan states: "Feeds — Bookmark, Reply, RSVP yes; Like, Repost no — Like/Repost are a low-value firehose — no dedicated feed." There will be no src/feeds/reposts.xml.njk, no src/feeds/reposts.json.njk, and no feed URLs at /reposts/feed.xml or /reposts/feed.json.

The type is still reachable by humans at its archive URL /reposts/, and individual Repost pages are reachable at /reposts/<slug>/. Feed readers simply won't discover a Reposts-specific feed.

The verification step from the plan confirms this is a hard requirement: ! test -e dist/likes/feed.xml (and by extension dist/reposts/feed.xml) is expected to be absent in the built output. Accidentally adding a feed pair would constitute a regressions against the plan's explicit decision.

9. Navigation

Repost is intentionally left out of the Posts submenu.

The plan states: "Nav — add Bookmark, Reply, RSVP to the Posts submenu; leave Like, Repost out — avoids nav bloat for the pure-firehose, feedless types." No entry such as { text: 'Reposts', url: '/reposts/' } will be added to src/_data/navigation.js.

Reposts remain reachable at /reposts/ for anyone who knows the URL, but the type will not surface in the main site navigation.

Open item. The plan flags this as still open: "Nav inclusion of Like/Repost — currently excluded; include if you want them discoverable. (still open)" If discoverability becomes a priority, adding { text: 'Reposts', url: '/reposts/' } to the Posts submenu is the straightforward path. No structural change is needed — the archive and pages already exist; it is purely a navigation data decision.

12. Collection registration (wiring)

The plan specifies a Step 0 refactor before any Phase 3a type is added. After that refactor, Repost registration is a two-touch operation: add 'repost' to POST_TYPES in collections.js, and add one explicit layout alias in eleventy.config.js.

// src/_config/collections.js  (after Step 0 refactor)
export const POST_TYPES = ['article','note','reading','jam','watching',
                           'bookmark','reply','rsvp','like','repost'];  // repost added here
export const byCategory = cat => collection =>
  collection.getFilteredByGlob('./src/posts/**/*.md')
    .filter(item => item.data.category === cat)
    .reverse();

// eleventy.config.js  (after Step 0 refactor)
import { POST_TYPES, byCategory, showInSitemap, tagList } from './src/_config/collections.js';
// Collection registration — loops POST_TYPES:
POST_TYPES.forEach(t => eleventyConfig.addCollection(t, byCategory(t)));
// Layout alias — explicit, NOT looped:
eleventyConfig.addLayoutAlias('repost', 'repost.njk');

Why the layout alias is explicit, not looped. The plan warns: "Do NOT fold the layout aliases into this loop: POST_TYPES includes article, which has no article.njk (it uses layout: post), so a generic alias loop would emit a bogus addLayoutAlias('article','article.njk')." Each alias is added alongside the other shipped aliases, one per type.

Category names never enter tags, so "repost" will not pollute /tags/.

13. Webmentions

Webmention is the IndieWeb's federated response protocol: likes, replies, and reposts from other sites arrive as cross-site comments. Nothing here will be Repost-specific — the plumbing is shared by every post type and Repost will inherit it through the base layout and entry-footer.njk. Discovery is shipped; receiving and sending are deferred to the webmention milestone.

PieceStateWhere
Endpoint discoveryshipped (Phase 1)<link rel="webmention" href="https://webmention.io/johanedlund.se/webmention"> in <head> via src/_includes/head/meta-info.njk (repost will use layout: base).
Authorship h-cardshippedThe hidden h-entry block carried into repost.njk from the note.njk clone will carry u-url, p-name u-url rel="author", and a u-author h-card avatar so a receiver can attribute the post (§5).
Render slotwired, no-oprepost.njk → entry-footer.njk → partials/webmentions.njk, currently an empty stub — safe to call while the renderer is empty.
Receiving / renderingdeferredThe webmention milestone wires a webmention.io fetch (via @11ty/eleventy-fetch, ~24 h cache); webmentions.njk then groups received mentions by type (likes / replies / reposts / mentions).
SendingdeferredOutgoing webmentions aren't wired, so a Repost won't notify the original post yet.

h-entry nesting (§5). The only h-entry in the layout will be the hidden authorship block; the visible u-repost-of anchor and .e-content will sit outside it, so a strict parser won't tie the repost property to the h-entry. Harmless while sending is off; fix it when the sending side of the webmention milestone lands — see §5.
