post-type spec

Event

Planned · Phase 3b · type event · namespace /events/ · designed from the Phase 3 plan 22 May 2026

An Event post announces an event the author is hosting — a talk, a meetup, a workshop, a release. Its content is a real h-event: Event is the first post type to nest a microformat root inside the post (Photo/Audio/Video carried only u-* properties), carrying a name, start/end datetimes, a location, a canonical URL, and a status. The archive splits into Upcoming and Past at build time, and cancelled events stay visible. Event is a title-required type, and — unlike every other feed-eligible type so far — it ships with no feed.

Event is not RSVP. An Event post is the author hosting their own event (a real h-event with dt-start/p-location/eventStatus). An RSVP post (Phase 3a, already spec'd) is responding to someone else's event — u-in-reply-to pointing at the host's event URL plus a p-rsvp value (yes/no/maybe/interested). They are different verbs (hosting vs. responding) and share no fields; don't conflate them.

Provenance. Event is the fourth heavy Phase 3b increment (after Photo, then Audio + Video — its own increment, with Recipe to follow). The Phase 3 plan only outlines Event (h-event nested in h-entry; a status badge; the archive split into upcoming/past with cancelled events staying visible; a title-required permalink; a new card-event.njk). The frontmatter shape, the status values, the real-schema decision, and the no-feed call below are decisions of the 22 May 2026 design increment (_generated/Plan - Event post type (Phase 3b design).md), built on the plan — not invented to fill the page. "The plan specifies …" means the Phase 3 plan; "the design increment decides …" means the 22 May pass. Several mechanisms here do not exist in the codebase yet (the build-time date filter, schemas/Event.njk, card-event.njk, event.njk); each is marked to-build rather than asserted as wired.

Slug derives from the filename via | slugify — not from the title. Event is title-required (the plan marks Recipe and Event title-required), but "title-required" governs the content (an event needs a name), not the slug source: the permalink still slugs from page.fileSlug, the shipped convention.

Why slug from page.fileSlug, not title. Article is the one shipped type that slugs from title ("/articles/{{ title | slugify }}/index.html"), and TODO.md §2 flags it as fragile — a missing/empty title silently breaks the URL with no enforcement. Event being title-required does not mean it should repeat that pattern; the design increment keeps the robust page.fileSlug source (filename = title in the Obsidian authoring workflow). (design increment decision)

No feed. The shipped feed-bearing types ship an Atom + JSON Feed pair, and the other heavy types add their own (Photo a photo-aware body; Audio/Video an RSS 2.0 podcast feed). Event ships none — see §8 for the reasoning.

4. Frontmatter (planned)

The shape below is the planned authoring surface decided by the 22 May design increment. No sample file exists yet. category, layout, and permalink are not authored per-post — they come from the folder data file src/posts/event/event.json (see §1, §12). The event data is grouped in a nested event: object (mirroring Photo's photo: and Audio's audio: so the heavy types author alike):

---

date: 2026-05-22                                # required — publish timestamp (post chronology)

  location: "ZAKK, Düsseldorf"                 # recommended → p-location (plain text, v1)
  url:   https://indieweb.org/2026/Dusseldorf  # optional → u-url (canonical / signup)
  status: scheduled                            # optional → scheduled | cancelled | postponed | moved-online
description: "Two days of creating and improving our personal websites." # recommended → p-summary
draft: true                                    # optional
tags:
  - indieweb                                   # optional — topic tags, NOT the category

h-entry nesting caveat — DEFERRED, and sharper here. Modeling on watching.njk puts the visible h-event outside the only h-entry in the layout (the hidden authorship block). For Photo/Audio/Video this orphaned only u-* properties; Event is the first type to put a whole microformat root outside the entry, so a strict mf2 parser sees a standalone h-event rather than one nested in the post's h-entry. Accepted for v1 because webmention sending isn't wired yet (design increment decision — Johan's call). Fixed holistically in the webmention milestone — either give the post layouts a self-contained h-entry or restructure the shared chrome (which also fixes the existing types) — not as an Event-only one-off. Same deferral as every type; sharper consequence.

7. Archive — Upcoming / Past split

This is the section that makes Event a heavy type. The plan splits the archive into upcoming and past, with cancelled events staying visible. The design increment renders this as one page at /events/ with two sections, partitioned at build time (the design increment's decision — single URL, one nav entry):

{# planned — src/pages/events.njk #}
{%- set upcoming = collections.event | filterUpcoming | sortByStartAsc -%}
{%- set past     = collections.event | filterPast -%}

<section aria-labelledby="upcoming">
  <h2 id="upcoming">Upcoming</h2>
  {%- for post in upcoming %}{% include "partials/card-event.njk" %}{% endfor -%}
</section>

<section aria-labelledby="past">
  <h2 id="past">Past</h2>
  {%- for post in past %}{% include "partials/card-event.njk" %}{% endfor -%}
</section>
SectionContainsOrder
Upcomingevents whose end || start is at/after build time (§9)soonest event first (ascending by event.start)
Pastthe restmost recent first (descending)

Cancelled events stay visible. Status drives the badge, not the partition — a cancelled event sits in whichever section its date places it (Upcoming until its date passes, then Past), always rendered, with a "Cancelled" badge. It is never filtered out. (plan requirement)

Sort note. byCategory() returns the collection .reverse()-d (newest-published first — collections.js). The Upcoming list wants soonest event date first, so the page re-sorts by event.start ascending after filtering. That is a page-level concern, not a change to the shared collection.

Diverges from archive-listing.njk. The shared archive partial assumes a single paginated list; the two-section split renders two filtered lists instead, so events.njk likely does not reuse archive-listing.njk as-is. If the Past list grows long, paginating it (not Upcoming) is the natural approach — a build detail, not specified for v1. (open)

8. Feed — none (decision)

Event ships no feed (design increment decision — Johan's call). It is the first feed-eligible heavy type to ship feedless: Photo/Audio/Video all carry feeds; among the light types only Like/Repost (the pure firehose) are feedless.

Why no feedDetail
Events expireA chronological feed of events is mostly past entries no one can attend — low subscriber value.
"Upcoming" can't be a static feedA live "upcoming events" feed would have to drop entries as their dates pass; on a static site "now" is frozen at build (§9), so the feed would only be correct between rebuilds. Awkward to syndicate.
Still reachableEvents remain linkable and discoverable at /events/ (§7) and via nav (§11) — they just aren't pushed to feed readers.

If syndication is wanted later: .ics, not RSS. The natural syndication format for events is an iCalendar (.ics) feed of upcoming events that a calendar app can subscribe to — not an RSS/Atom firehose. Noted as a possible future add, not specified here. (open)

9. Build-time date filter (the to-build filter)

The upcoming/past partition (§7) needs a build-time date comparison: "is this event still upcoming as of now?" No such helper exists. src/_config/filters/dates.js holds only toISOString (dayjs → ISO-8601) and formatDate (dayjs format) — no comparison filter (verified, 22 May 2026). So this is real, small build work:

// planned — src/_config/filters/events.js
export const isUpcoming = (event) => {
  const boundary = event?.end || event?.start;     // an in-progress event counts as upcoming until its end
  return new Date(boundary) >= new Date();          // "now" = build time (static site)
};
export const isPast = (event) => !isUpcoming(event);

// collection filters used by events.njk (§7):
export const filterUpcoming = (posts) => posts.filter(p => isUpcoming(p.data.event));
export const filterPast     = (posts) => posts.filter(p => isPast(p.data.event));
export const sortByStartAsc = (posts) => [...posts].sort((a, b) =>
  new Date(a.data.event.start) - new Date(b.data.event.start));
PieceSourceState
Upcoming/past partitionevent.end || event.start vs build-time Datefilter — to-build
Sort within Upcomingevent.start ascendingfilter — to-build
RegistrationaddFilter in eleventy.config.js (like the other filters)to-build

"Now" is build time. Because the site is static, an event only moves from Upcoming to Past when the site is rebuilt — fine for a site that rebuilds on a schedule or on deploy, but worth stating: the partition is correct as of the last build, not in real time. Boundary handling (an event that has started but not ended counts as upcoming until end; an event with no end uses start) and the exact filter-vs-collection wiring are build details flagged here, not a finished solution. (to-build)

10. JSON-LD / Schema.org — real Event

Event breaks the BlogPosting v1 pattern the other heavy types set (design increment decision — Johan's call). Photo/Audio/Video keep BlogPosting precisely because their richer schema templates don't exist yet; Event instead commits to a real schema.org/Event now, because it is by far the strongest rich-results candidate (Google surfaces event rich results from startDate/location/eventStatus).

Hard dependency: the template ships with the frontmatter. The schema include is {%- include "schemas/" + schema + ".njk" -%} (src/_includes/head/schema.njk:4), which throws if the template is missing. Only BlogPosting.njk and WebSite.njk exist (verified). So schema: Event cannot be set until schemas/Event.njk is created — the template and the frontmatter must land in the same change. This is the one place Event diverges from the "keep BlogPosting v1, defer the real schema" approach the other heavy types took; it is a deliberate, scoped exception, not a defer.

Location modeling is v1-simple. The rule above (url + no location → VirtualLocation; otherwise Place { name }) covers the common physical-vs-online case. A structured address (PostalAddress), hybrid in-person+online events (eventAttendanceMode: MixedEventAttendanceMode with both a Place and a VirtualLocation), and optional offers/performer/image are deferred. (open — §15)

11. Navigation

Event gets a nav entry. The plan's light-type rule gates nav on having a feed (feed-bearing types are surfaced; the pure-firehose Like/Repost are not), but Event is a substantive content type, not a firehose — so it is surfaced even though it has no feed (design increment decision). Added to the Posts submenu in src/_data/navigation.js:

{ text: 'Event', url: '/events/' }

Planned — not yet added. Nav inclusion here is decoupled from the feed decision (§8): a type can be discoverable without being subscribable.

12. Collection registration (wiring)

Event registers through the same POST_TYPES mechanism the light types use (introduced by the Phase 3a Step 0 refactor):

// src/_config/collections.js
export const POST_TYPES = ['article','note','reading','jam','watching', ... ,'event'];

// eleventy.config.js
POST_TYPES.forEach(t => eleventyConfig.addCollection(t, byCategory(t)));

// Layout alias — added explicitly, NOT looped over POST_TYPES:
eleventyConfig.addLayoutAlias('event', 'event.njk');

// register the date filters (§9):
eleventyConfig.addFilter('filterUpcoming', filterUpcoming);
eleventyConfig.addFilter('filterPast', filterPast);
eleventyConfig.addFilter('sortByStartAsc', sortByStartAsc);

Layout aliases stay explicit. Do NOT fold layout aliases into the POST_TYPES.forEach loop — POST_TYPES includes article, which has no article.njk (it uses layout: post), so a generic alias loop would emit a bogus alias. Each new type's alias is added explicitly.

Category names never enter tags, so "event" does not pollute /tags/.

15. Status & open items

Planned — not built; design detailed in the 22 May 2026 increment. See _generated/Plan - Phase 3 (10 new post types) - final.md §Phase 3b and _generated/Plan - Event post type (Phase 3b design).md.

  • Phase 3b — no files for this type exist yet. The POST_TYPES refactor (Phase 3a Step 0) is a prerequisite for the wiring in §12.
  • h-event shape — DECIDED. Nested event: { start, end?, location, url?, status } + title (= p-name) + description (= p-summary). No redundant event.name. See §4.
  • Status — DECIDED: schema.org EventStatusType (scheduled/cancelled/postponed/moved-online). Drives the badge and eventStatus; cancelled events stay visible. See §5, §7, §10.
  • Archive split — DECIDED: one page, Upcoming + Past sections, partitioned at build time; cancelled events partition by date and stay visible. See §7.
  • Build-time date filter — to-build. dates.js has no comparison helper (verified); a new events.js filter compares event.end || event.start to build-time Date. "Now" is frozen at build. See §9.
  • Schema — DECIDED: real schema.org/Event as v1 (breaks the BlogPosting pattern the other heavy types kept). schemas/Event.njk is to-build and must ship with schema: Event (the include throws on a missing template). See §10.
  • Feed — DECIDED: none. Events expire; a live "upcoming" feed can't be statically correct. An .ics calendar feed is the natural future syndication format, not RSS. See §8.
  • Location — v1 plain-text p-location + optional u-url. Structured address (h-card/h-adr, PostalAddress), hybrid attendance mode, and offers/performer/image are deferred. See §4, §10.
  • Bespoke card — card-event.njk (date-led, not image-led, not card-response.njk). The day/month + status badge CSS is a small to-build block. See §6.
  • Title-required, but slug from page.fileSlug — not from title (sidesteps Article's fragile title-derived permalink, TODO.md §2). See §3.
  • Archive pagination — open. If the Past list grows long, paginate it (not Upcoming); v1 can render all. events.njk likely diverges from the shared archive-listing.njk. See §7.
  • µf2 h-entry nesting — DEFERRED + documented (v1). Sharper than prior types — Event orphans a microformat root, not just properties — but fixed holistically in the webmention milestone, not as an Event-only one-off. See §5, §14.
  • Not RSVP. Event = hosting your own event (h-event); RSVP = responding to someone else's (u-in-reply-to + p-rsvp). See the intro note.
