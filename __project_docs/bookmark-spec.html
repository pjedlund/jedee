post-type spec

Bookmark

Planned · Phase 3a · singular bookmark / plural bookmarks · derived from the Phase 3 plan 22 May 2026

A Bookmark is a short post recording a URL worth keeping — a page, article, or resource the author wants to preserve and optionally annotate. The IndieWeb "bookmark" post type: a deliberate save, not a passive browser history entry.

1. Singular / plural identity

Bookmark is asymmetric: the type is singular, the URL namespace is plural. The Eleventy collection will be named with the singular (collections.bookmark), but the folder, URL, archive, and feed will all use the plural.

Note the mismatch: the folder will be bookmarks/ but its data file will set category: "bookmark", and the collection registered from that category will be bookmark (singular). Don't "fix" this — the layout alias, collection, and category are all singular by design.

2. Naming & aliases

JEDEE's bookmarking type is named Bookmark (singular) / Bookmarks (plural), following the IndieWeb's established "bookmark" post type. It maps directly to the IndieWeb "bookmark" verb: saving a URL for later reference, with an optional annotation.

TermStatusWhere it appears / why
bookmark / bookmarkschosen nameType, layout, collection, URL, archive, feed, nav (see §1).
bookmarkIndieWeb verbThere is no separate microformat vocabulary word: the property is u-bookmark-of and the IndieWeb verb is "bookmark." The type name and the IndieWeb verb are the same word.

4. Frontmatter (planned)

The shape below is the planned authoring surface for a Bookmark post. No sample file exists yet; the plan specifies the field set. category, layout, and permalink are not authored per-post — they will come from the folder data file src/posts/bookmarks/bookmarks.json (see §1 and §12).

---
title: Some Bookmarked Page Title     # optional
bookmarkOf: https://example.com/page  # required — the bookmarked URL → u-bookmark-of
date: 2026-06-01T10:00:00+02:00       # required — post timestamp
description: A short annotation.      # recommended
draft: true                           # optional
tags:
  - topic                             # optional — topic tags, NOT the category
---
FieldReq?Role
bookmarkOfrequired for µf2The bookmarked URL → rendered as u-bookmark-of. camelCase because Nunjucks cannot read hyphenated top-level keys (see §5).
titleoptionalHeadline; falls back to slug. Title-optional type.
daterequiredPost timestamp (sort + dt-published).
descriptionrecommendedCard excerpt and feed summary. Serves as the annotation / commentary on the bookmarked URL.
draftoptionalWhen true, the card shows a "draft" badge; post is still built.
tagsoptionalTopic tags. Not the category.

The bookmarkOf field is camelCase by a locked decision (see §5). The IndieWeb property name u-bookmark-of lives in the µf2 class on the rendered anchor, not in the YAML key.

5. Microformats (µf2)

The layout will be src/_layouts/bookmark.njk (planned). The plan specifies that the bookmark target is a visible verb + anchor — the µf2 class goes on a visible <a> element, not a hidden <data> element. This is because bookmark posts are often body-less: the target URL is the content, so it must be visible.

The plan specifies the planned layout body:

<p>Bookmarked <a class="u-bookmark-of" href="{{ bookmarkOf }}">{{ bookmarkOf }}</a></p>
<div class="e-content">{{ content | safe }}</div>

Contrast with Jam: Jam uses a hidden <data hidden class="u-listen-of"> because it always has a visible body (album metadata, review text). Bookmark, Like, Reply, and Repost use a visible anchor because the target is the post content for body-less entries.

PropertyClassFrom
Bookmark targetu-bookmark-ofbookmarkOf
Bodye-contentpost content (may be empty)
Publisheddt-publisheddate (via entry-header → date.njk)
Authorshiph-entry / h-card / u-authorhidden block, meta.author

camelCase field name — LOCKED. The frontmatter key is bookmarkOf (camelCase) because Nunjucks cannot read hyphenated top-level keys: bookmark-of would be parsed as subtraction. The IndieWeb semantics live in the µf2 class (u-bookmark-of on the rendered anchor), not in the YAML key. This decision is locked for all five Phase 3a light types.

h-entry nesting caveat — DEFERRED. Cloning note.njk puts the visible u-bookmark-of anchor and .e-content outside the only h-entry in the layout (the hidden authorship block), so a strict mf2 parser won't tie the bookmark property to the entry. Accepted for v1 because webmention sending isn't wired up yet. Fix in the webmention milestone — either give the bookmark layout a proper self-contained h-entry, or restructure note.njk and the shared chrome.

6. Card

Bookmark will use the shared card-response.njk partial (planned). This is one card for all five Phase 3a light types (Bookmark, Like, Reply, Repost, RSVP), modeled on card-notes.njk but dropping the title/headline assumption — these posts are often title-less. It will render a <custom-card clickable> WebC component with no image slot, bundling css/custom-card.css.

SlotContent

Planned — not yet built. The card-response.njk partial does not exist yet; it will be created in Phase 3a Step 1, before the individual types are wired up. The card is shared across all five light types; Bookmark is not the only consumer.

8. Feed

Bookmark gets a feed — the plan lists it as "✅ Feed." A pair of templates will be cloned from src/feeds/notes.json.njk and notes.xml.njk to src/feeds/bookmarks.json.njk and bookmarks.xml.njk. The plan specifies updating the permalink: frontmatter — this, not the filename, controls the output path:

# bookmarks.xml.njk
permalink: /bookmarks/feed.xml
feedCollection = collections.bookmark
feedTitle = "Bookmarks"
feedDescription = "Pages and resources I've bookmarked."
feedSelfUrl = "/bookmarks/feed.xml"
→ includes feeds/atom-body.njk

# bookmarks.json.njk — same vars, with:
permalink: /bookmarks/feed.json
feedSelfUrl = "/bookmarks/feed.json"
→ includes feeds/json-body.njk

The permalink: frontmatter (not the filename) controls the output path. The plan warns that leaving a cloned permalink: /notes/feed.xml in place collides with the Notes feed and errors the build.

Title-less entries — open question. Bookmark is a title-optional type. Title-less entries produce an empty <title> element in the Atom feed. The plan flags this wrinkle: the open question is whether to compute a fallback title (e.g. deriving the hostname from bookmarkOf) or accept an empty <title> for v1. This is not resolved in the plan — see §14.

9. Navigation

Bookmark gets a nav entry — the plan lists it as "✅ Nav." The plan specifies adding to the Posts submenu in src/_data/navigation.js:

{ text: 'Bookmarks', url: '/bookmarks/' }

Planned — not yet added. Like and Repost are excluded from the nav (plan: "Avoids nav bloat for the pure-firehose, feedless types"). Bookmark, Reply, and RSVP are included.

12. Collection registration (wiring)

Phase 3a begins with a refactor (Step 0) that collapses per-type collection registration into a POST_TYPES array. The plan specifies:

// src/_config/collections.js — after the Step 0 refactor
export const POST_TYPES = ['article','note','reading','jam','watching','bookmark',...];
export const byCategory = cat => collection =>
  collection.getFilteredByGlob('./src/posts/**/*.md')
    .filter(item => item.data.category === cat)
    .reverse();

// eleventy.config.js — after the Step 0 refactor
import { POST_TYPES, byCategory, showInSitemap, tagList } from './src/_config/collections.js';
POST_TYPES.forEach(t => eleventyConfig.addCollection(t, byCategory(t)));

// Layout alias — added explicitly, NOT looped over POST_TYPES:
eleventyConfig.addLayoutAlias('bookmark', 'bookmark.njk');

Layout aliases stay explicit. The plan is clear: do NOT fold layout aliases into the POST_TYPES.forEach loop. POST_TYPES includes article, which has no article.njk (it uses layout: post), so a generic alias loop would emit a bogus addLayoutAlias('article','article.njk'). Each new type's alias is added explicitly alongside the shipped aliases.

Category names never enter tags, so "bookmark" does not pollute /tags/.

13. Webmentions

Webmention is the IndieWeb's federated response protocol: likes, replies, and reposts from other sites arrive as cross-site comments. Nothing here is Bookmark-specific — the plumbing is shared by every post type and Bookmark will inherit it through the base layout and entry-footer.njk. Discovery is shipped; receiving and sending are deferred to the webmention milestone.

PieceStateWhere
Endpoint discoveryshipped (Phase 1)<link rel="webmention" href="https://webmention.io/johanedlund.se/webmention"> in <head> via src/_includes/head/meta-info.njk (bookmark will use layout: base).
Authorship h-cardplannedThe hidden h-entry block cloned from note.njk into bookmark.njk will carry u-url, p-name u-url rel="author", and a u-author h-card avatar so a receiver can attribute the post (§5).
Render slotplanned, will be no-opbookmark.njk → entry-footer.njk → partials/webmentions.njk, currently an empty stub — safe to call while the renderer is empty.
Receiving / renderingdeferredThe webmention milestone wires a webmention.io fetch (via @11ty/eleventy-fetch, ~24 h cache); webmentions.njk then groups received mentions by type (likes / replies / reposts / mentions).
SendingdeferredOutgoing webmentions aren't wired, so a Bookmark that responds to another post won't notify it yet.

h-entry nesting (§5). The only h-entry in the layout will be the hidden authorship block; the visible u-bookmark-of anchor and .e-content will sit outside it, so a strict parser won't tie the bookmark target to the entry. Harmless while sending is off; fix it when the sending side of the webmention milestone lands — see §5 and §14.
