Interlinker: the async-shortcode trap & its scaling ceiling

Why the main nav rendered empty, the one-line fix, and a measured reason the same plugin can't scale to a Tolstoy-sized vault. Companion warning for the Tolstoy team: docs/architecture/eleventy-interlinker-scaling-warning.md.

TL;DR. The @photogabble/eleventy-plugin-interlinker wikilinks plugin resolves links by re-entering Eleventy's render pipeline once per page (a per-page eleventyComputed function that calls page.template.read() and depends on collections.all). That one design choice causes both problems on this page: (1) it silently drops the output of an async shortcode reached through an {% if %}-wrapped {% include %} — which blanked our whole nav with no error; and (2) its build cost and especially its memory grow steeply with page count — fine at hundreds of pages, fatal at tens of thousands.

1. The symptom

With the nav revealed, {% include "partials/main-nav.njk" %} rendered to zero bytes — no <nav>, no links, no error, exit code 0. The header logo ({% svg "misc/logo" %}) and footer icons rendered fine; only the nav vanished. It went unnoticed because the nav was hidden for the soft-launch.

2. Root cause — three ingredients

The blank requires all three at once; remove any one and it renders:

  1. the interlinker plugin is active (it runs a whole-site link-resolution render pass);
  2. an async shortcode is involved — our {% svg %} was needlessly async (a stray await around svgo's optimize(), which is synchronous: a vestige of svgo v1's Promise API);
  3. that shortcode is reached through an {% include %} that is itself wrapped in an {% if %} / {% for %} block.

A bare {% include %} of the identical partial renders the same async shortcode fine — which is the trap: wrapping an existing include in an ordinary conditional is what breaks it.

3. Why it was invisible

A git bisect (272 commits, dependencies pinned constant) landed on exactly one commit: the go-live / soft-launch commit (3975491). Its only nav-path change was wrapping the include to hide it:

-    {% include "partials/main-nav.njk" %}
+    {% if not meta.navigation.hideNav %}
+      {% include "partials/main-nav.njk" %}
+    {% endif %}

That same commit also set hideNav: true. So the nav broke and was hidden in the same atomic commit — it was structurally impossible to notice. The earlier belief that it "worked at launch" was correct: it worked right up to that commit, with a bare include.

4. The fix

One file, src/_config/shortcodes/svg.js: drop the gratuitous async/await so {% svg %} returns a plain string. With no Promise to drop, interlinker can't blank it, and the conditional is safe again. This also future-proofs every other {% svg %} call. Merged to main (fix/nav-empty-render → 87d9f99).

Latent risk that remains. {% image %} / {% imageKeys %} (eleventy-img) are genuinely async and can't be made sync. If one is ever placed inside an {% if %}-wrapped nested {% include %} while interlinker is active, it will blank the same way. Keep async shortcodes out of conditionally-included partials, or move the conditional inside the partial.

5. How it was isolated

The decisive control was a vanilla Eleventy Excellent 4.6.1 checkout with the identical nav markup: it rendered the chevron fine. Diffing the two repos ruled out the shortcode (byte-identical), the registration, the include depth, and the dependency versions (svgo 4.0.1 / nunjucks 3.2.4 / eleventy 3.1.5 — all equal). The one difference was interlinker, which vanilla EE doesn't ship. Disabling interlinker, or making the shortcode sync, each independently restored the nav.

6. The deeper issue — interlinker doesn't scale

The same render-reentry that ate the nav is also a scaling tax. Measured on a throwaway harness (N synthetic notes, 10 wikilinks each, Eleventy 3.1.5 / interlinker 1.1.2 / Node 22), interlinker OFF vs ON, build time + peak resident memory:

Two readings. Time grows roughly linearly until ~4k notes, then turns super-linear (the collections.all-per-page term, ≈O(N²), overtakes): 4k→8k is a 2.7× jump for 2× the notes. Memory is the binding constraint — the baseline stays flat (~370 MB at 8k) while interlinker's overhead roughly doubles every doubling, reaching 4.2 GB at 8,000 notes. The plain-Eleventy (OFF) column is also a fair proxy for a parse-level wikilinks approach, which never re-enters the render pipeline.

7. Extrapolation to a large vault

Beyond the 8k measured ceiling these are extrapolations, but the memory wall is disqualifying long before time matters:

8. Recommendations

  • JEDEE: keep interlinker. Hundreds of pages is exactly where it's fine, and the sync-{% svg %} fix neutralizes the async fragility. No action beyond the fix already merged.
  • Anything at thousands-of-pages scale: do not resolve wikilinks in the render pipeline. Pre-compute the link/backlink graph in a build step before Eleventy (a script, or a markdown-it parse-level rule for inline [[ ]] + a single post-render HTML scan for backlinks). That's O(content), single-pass, and never touches async rendering. See the Tolstoy warning doc for the concrete migration.
  • Never put an async shortcode inside an {% if %}-wrapped {% include %} while interlinker is active. Documented in the eleventy-excellent and indieweb skills.

9. Reproduce

The throwaway harness: a minimal Eleventy project, a generator (gen.mjs N K) that writes N interlinked notes, and a sweep runner that builds each size with interlinker on and off, capturing Eleventy's reported time and peak RSS via /usr/bin/time -l. Toggle is INTERLINKER=1 in the config. The "OFF" build is the floor a parse-level approach would sit near.
