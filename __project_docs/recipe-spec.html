post-type spec

Recipe

Planned · Phase 3b · type recipe · namespace /recipes/ · designed from the Phase 3 plan 22 May 2026

A Recipe post publishes a recipe the author has written — ingredients, steps, yield, and timing. Its content is a real h-recipe: Recipe is the second post type to nest a microformat root inside the post (after Event; Photo/Audio/Video carried only u-* properties), carrying a name, summary, yield, a total duration, a repeated ingredient list, an instructions block, and an optional dish photo. Recipe is a title-required type, and — unlike Event — it ships a feed (recipes don't expire, so a recipe feed is genuinely followable, like Photo). It is the fifteenth and last type; this spec completes the set.

Recipe is structured data, not a food article. A long-form post that happens to mention cooking is an Article. A Recipe post is the deliberate, structured form: ingredients and instructions live in frontmatter arrays (not just prose), so the layout can emit a real h-recipe (µf2) and a real schema.org/Recipe (JSON-LD) — which is what earns Google's recipe rich results. The markdown body is for the headnote / story; the recipe itself is data.

Provenance. Recipe is the fifth and last heavy Phase 3b increment (after Photo, then Audio + Video, then Event). The Phase 3 plan only outlines Recipe (h-recipe nested in h-entry; structured recipeIngredient[] / recipeInstructions[]; an ISO-8601 duration filter accepting integer minutes and PT…M; a title-required permalink). The ingredients/instructions data model, the real-schema decision, the feed call, the bespoke card, and the archive shape below are decisions of the 22 May 2026 design increment (_generated/Plan - Recipe post type (Phase 3b design).md), built on the plan — not invented to fill the page. "The plan specifies …" means the Phase 3 plan; "the design increment decides …" means the 22 May pass. Several mechanisms here do not exist in the codebase yet (the duration filter, schemas/Recipe.njk, card-recipe.njk, recipe.njk, the recipe-aware feed body); each is marked to-build rather than asserted as wired.

Slug derives from the filename via | slugify — not from the title. Recipe is title-required (the plan marks Recipe and Event title-required), but "title-required" governs the content (a recipe needs a name), not the slug source: the permalink still slugs from page.fileSlug, the shipped convention.

Why slug from page.fileSlug, not title. Article is the one shipped type that slugs from title ("/articles/{{ title | slugify }}/index.html"), and TODO.md §2 flags it as fragile — a missing/empty title silently breaks the URL with no enforcement. Recipe being title-required does not mean it should repeat that pattern; the design increment keeps the robust page.fileSlug source (filename = title in the Obsidian authoring workflow). (design increment decision)

4. Frontmatter (planned)

The shape below is the planned authoring surface decided by the 22 May design increment. No sample file exists yet. category, layout, and permalink are not authored per-post — they come from the folder data file src/posts/recipe/recipe.json (see §1, §13). The recipe data is grouped in a nested recipe: object (mirroring Photo's photo:, Audio's audio:, and Event's event: so the heavy types author alike). Ingredients and instructions are frontmatter string arrays (the core design decision — structured enough to emit µf2 + schema without parsing the rendered body):

---
title: "Sourdough focaccia"                    # required → p-name (title-required type)
date: 2026-05-22                               # required — publish timestamp (post chronology)
description: "Olive-oil rich, dimpled flatbread." # recommended → p-summary
recipe:
  yield: "8 servings"                          # recommended → p-yield / recipeYield
  prepTime: 30                                 # optional → schema prepTime (int minutes OR PT…M)
  cookTime: 25                                 # optional → schema cookTime (int minutes OR PT…M)
  totalTime: PT4H                              # optional → dt-duration / totalTime (drives the page time)
  ingredients:                                 # required → p-ingredient (repeated) / recipeIngredient[]
    - "500 g bread flour"
    - "12 g fine sea salt"
    - "400 g water"
  instructions:                                # required → e-instructions / recipeInstructions[]
    - "Mix flour, water, salt; autolyse 1 hr."
    - "Fold every 30 min, 4 times; proof overnight."
    - "Dimple, top with oil; bake 25 min at 230°C."
  image: ./focaccia.jpg                        # optional → u-photo / schema image
draft: true                                    # optional
tags:
  - bread                                      # optional — topic tags, NOT the category
---

How u-photo lands on the <img>. The dish photo reuses Eleventy Excellent's image shortcode, which puts a caller-supplied class on the generated <img> via its imageClass parameter (src/_config/shortcodes/image.js:70, verified for Photo) — so {% image recipe.image, '', 'u-photo' %} emits the u-photo class correctly. The same shortcode also hardcodes slot="image" (image.js:74); outside a <custom-card> that attribute is inert, so it's harmless on the post page (it matters only in the card — §6).

h-entry nesting caveat — DEFERRED, and sharper here. Modeling on watching.njk puts the visible h-recipe outside the only h-entry in the layout (the hidden authorship block). Like Event, Recipe puts a whole microformat root outside the entry (Photo/Audio/Video orphaned only u-* properties), so a strict mf2 parser sees a standalone h-recipe rather than one nested in the post's h-entry. Accepted for v1 because webmention sending isn't wired yet (design increment decision — Johan's call, consistent with Event). Fixed holistically in the webmention milestone — either give the post layouts a self-contained h-entry or restructure the shared chrome (which also fixes the existing types) — not as a Recipe-only one-off. Same deferral as every type; sharper consequence (shared with Event).

7. Archive — chronological grid

Unlike Event's upcoming/past split, Recipe has no special partition: recipes don't expire, so the archive is a standard chronological grid at /recipes/ (newest first), rendering card-recipe.njk — the same shape as the shipped /notes/ and /jams/ archives (design increment decision — masonry was considered, given the image-led card, and declined for v1).

Sort is already right. byCategory() returns the collection .reverse()-d (newest-published first — collections.js), which is exactly what a chronological archive wants — so, unlike Event, the page needs no re-sort. Whether recipes.njk reuses the shared archive-listing.njk verbatim or needs a small override to swap in card-recipe.njk is a build detail. (open)

8. Feed — Atom + JSON Feed (recipe-aware body)

Recipe ships a feed (design increment decision — Johan's call): recipes don't expire, so a recipe feed is genuinely followable (the opposite of Event, which ships feedless because events expire). It uses the site's standard followable-type format — an Atom + JSON Feed pair, like Photo and the shipped types — not the Audio/Video RSS 2.0 podcast shape.

The feed wrinkle — why a recipe-aware body is required. The shared feed bodies emit only post.content via renderTransforms (verified: src/_includes/feeds/atom-body.njk:37, json-body.njk:27) — no frontmatter fields. Recipe's ingredients and instructions live in frontmatter (§4), so a naive clone of the notes feed would syndicate only the headnote and drop the entire recipe (the same lesson Photo's frontmatter image surfaced). The fix is a new recipe-body.njk that renders post.content plus the structured ingredients/instructions (and yield/time, and an absolute-URL dish image when present), so subscribers get the whole recipe. The exact rendering (an HTML list appended to the content) is a build detail; v1 names the recipe-aware approach. (to-build)

9. ISO-8601 duration filter (the to-build filter)

The recipe times (§4) accept two input forms — an integer number of minutes or an ISO-8601 PT… string — and need two outputs: a normalized PT…M for dt-duration (µf2) + schema prepTime/cookTime/totalTime, and a human-readable string for the page and card. No duration filter exists. src/_config/filters/dates.js holds only toISOString (dayjs → ISO-8601) and formatDate (dayjs format) — and Audio's itunes:duration formatter is a different output shape (HH:MM:SS). So this is real, new build work — the plan's headline mechanism for Recipe:

// planned — src/_config/filters/duration.js
// Accepts an integer number of minutes OR an ISO-8601 "PT…" string.

// (a) normalized ISO-8601 → dt-duration (µf2) + schema prep/cook/totalTime
export const toISODuration = (input) => {
  if (typeof input === 'number') return `PT${input}M`;     // 90 → "PT90M"
  return input;                                            // "PT1H30M" → unchanged
};

// (b) human-readable → the page + card ("1 hr 30 min", "55 min", "4 hr")
export const formatDuration = (input) => {
  const mins = toMinutes(input);                           // 90  or  "PT1H30M" → 90
  const h = Math.floor(mins / 60), m = mins % 60;
  return [h && `${h} hr`, m && `${m} min`].filter(Boolean).join(' ');
};

10. JSON-LD / Schema.org — real Recipe

Recipe breaks the BlogPosting v1 pattern that Photo/Audio/Video kept (design increment decision — Johan's call), exactly as Event did. Those types stay on BlogPosting precisely because their richer schema templates don't exist yet; Recipe instead commits to a real schema.org/Recipe now, because it is an even stronger rich-results candidate than Event — Google's recipe rich cards surface image, time, yield, and ingredients directly from this markup.

12. Collection registration (wiring)

Recipe registers through the same POST_TYPES mechanism the light types use (introduced by the Phase 3a Step 0 refactor):

// src/_config/collections.js
export const POST_TYPES = ['article','note','reading','jam','watching', ... ,'recipe'];

// eleventy.config.js
POST_TYPES.forEach(t => eleventyConfig.addCollection(t, byCategory(t)));

// Layout alias — added explicitly, NOT looped over POST_TYPES:
eleventyConfig.addLayoutAlias('recipe', 'recipe.njk');

// register the duration filters (§9):
eleventyConfig.addFilter('toISODuration', toISODuration);
eleventyConfig.addFilter('formatDuration', formatDuration);

Layout aliases stay explicit. Do NOT fold layout aliases into the POST_TYPES.forEach loop — POST_TYPES includes article, which has no article.njk (it uses layout: post), so a generic alias loop would emit a bogus alias. Each new type's alias is added explicitly.

Category names never enter tags, so "recipe" does not pollute /tags/.
