post-type spec

Like

Planned · Phase 3a · singular like / plural likes · derived from the Phase 3 plan 22 May 2026

A Like is a short post expressing appreciation for something on the web — linking to the liked URL with an explicit endorsement signal. The IndieWeb "like" post type: no body required, the target URL is the content.

1. Singular / plural identity

Like is asymmetric: the type is singular, the URL namespace is plural. The Eleventy collection will be named with the singular (collections.like), but the folder, URL, and archive all use the plural. Like has no feed and no nav entry (see §8, §9).

2. Naming & aliases

JEDEE's endorsement type is named Like (singular) / Likes (plural), mapping directly to the IndieWeb "like" post type — an explicit, curated expression of appreciation for something on the web.

TermStatusWhere it appears / why
like / likeschosen nameType, layout, collection, URL, archive (see §1). No feed, no nav.
likeIndieWeb verbThe microformat property is u-like-of. Like maps directly to IndieWeb's like vocabulary — no alias or renaming needed.

Slug derives from the filename via | slugify. Like is a title-optional type (plan Decision 9) — the filename is the slug source. There is no feed URL: Like has no dedicated feed (see §8).

camelCase URL field (LOCKED). The frontmatter key is likeOf, not like-of. Nunjucks cannot read hyphenated top-level keys (like-of parses as subtraction). IndieWeb semantics live in the µf2 class (u-like-of) on the rendered anchor, not in the frontmatter key name. This decision is locked for all Phase 3a types.

category, layout, and permalink will not be authored per-post — they will come from the folder data file src/posts/likes/likes.json (see §1 and §12). The folder data file will also set tags: "posts" (the system tag) so Likes appear in the global posts collection; this is separate from per-post topic tags.

5. Microformats (µf2)

The layout src/_layouts/like.njk WILL emit a visible verb + anchor. The plan specifies this exact Like example:

<p>Liked <a class="u-like-of" href="{{ likeOf }}">{{ likeOf }}</a></p>
<div class="e-content">{{ content | safe }}</div>

The µf2 target is a visible anchor — not a hidden <data> element. Like posts have no body: the target URL is the content and cannot be hidden. (Contrast Jam, which uses a hidden <data class="u-listen-of"> because it carries a separate visible body.)

PropertyClassFrom
Like targetu-like-oflikeOf — visible <a>
Bodye-contentpost content (usually empty for a Like)
Publisheddt-publisheddate (via entry-header → date.njk)
Authorshiph-entry / h-card / u-authorhidden block, meta.author

h-entry nesting caveat (DEFERRED). Cloning note.njk places the visible u-like-of anchor and .e-content outside the only h-entry in the layout (the hidden authorship block), so a strict mf2 parser won't tie the like property to the entry. Accepted for v1 — webmention sending isn't wired up yet. Flagged for the webmention milestone: either give the response layouts a proper self-contained h-entry, or restructure note.njk and the shared chrome (the latter also fixes existing types).

8. Feed

Like has no dedicated feed — this is a deliberate design decision.

There will be no likes.json.njk or likes.xml.njk. The plan states: Like (together with Repost) is a low-value firehose — publishing every liked URL as a feed entry would flood subscribers with low-signal noise. Likes are reachable at their archive URL (/likes/) for anyone who wants to browse them, but they are excluded from feed output.

This is a first-class design decision, not an omission. Of the five Phase 3a light types, Bookmark, Reply, and RSVP each get Atom + JSON feeds; Like and Repost deliberately do not. If a future decision reverses this (e.g. to power a Micropub-compatible feed reader), a feed pair can be added following the same pattern as notes.{xml,json}.njk.

9. Navigation

Like is intentionally left out of the Posts submenu.

Like will not have a nav entry in src/_data/navigation.js. The plan decision: avoid nav bloat for the pure-firehose, feedless types. The Likes archive is still reachable directly at /likes/. Of the five Phase 3a light types, only Bookmark, Reply, and RSVP are added to the Posts submenu.

Open item. Nav inclusion of Like (and Repost) is flagged open in the plan: "include if you want them discoverable." If discoverability at the nav level is wanted later, add { text: 'Likes', url: '/likes/' } to the Posts submenu in src/_data/navigation.js. Nothing needs to change in the type implementation itself.

12. Collection registration (wiring)

The plan specifies a POST_TYPES array refactor (Step 0) that collapses collection registration to a loop. The Like type will be added as one entry in that array. The layout alias must be added explicitly — not looped — because POST_TYPES includes article, which has no article.njk (it uses layout: post), so a generic alias loop would emit a bogus addLayoutAlias('article','article.njk').

// src/_config/collections.js (planned shape)
export const byCategory = cat => collection =>
  collection.getFilteredByGlob('./src/posts/**/*.md')
    .filter(item => item.data.category === cat)
    .reverse();

export const POST_TYPES = ['article','note','reading','jam','watching',
                           'bookmark','reply','rsvp','like','repost'];
// POST_TYPES.forEach drives addCollection in eleventy.config.js

// eleventy.config.js (planned additions)
import { POST_TYPES, byCategory, showInSitemap, tagList } from './src/_config/collections.js';
POST_TYPES.forEach(t => eleventyConfig.addCollection(t, byCategory(t)));
eleventyConfig.addLayoutAlias('like', 'like.njk');   // explicit — not looped

Category names never enter tags, so "like" will not pollute /tags/.

The folder data file src/posts/likes/likes.json will set layout: "like" (extensionless) — which is why the layout alias is required. The data file will also set category: "like", tags: "posts", and the permalink pattern.

13. Webmentions

Webmention is the IndieWeb's federated response protocol: likes, replies, and reposts from other sites arrive as cross-site comments. Nothing here is Like-specific — the plumbing is shared by every post type and Like will inherit it through the base layout and entry-footer.njk. Discovery is shipped; receiving and sending are deferred to the webmention milestone.

PieceStateWhere
Endpoint discoveryshipped (Phase 1)<link rel="webmention" href="https://webmention.io/johanedlund.se/webmention"> in <head> via src/_includes/head/meta-info.njk (like will use layout: base).
Authorship h-cardwill be shipped (cloned from note.njk)The hidden h-entry block in like.njk will carry u-url, p-name u-url rel="author", and a u-author h-card avatar so a receiver can attribute the post (§5).
Render slotwill be wired, no-oplike.njk → entry-footer.njk → partials/webmentions.njk, currently an empty stub — safe to call while the renderer is empty.
Receiving / renderingdeferredThe webmention milestone wires a webmention.io fetch (via @11ty/eleventy-fetch, ~24 h cache); webmentions.njk then groups received mentions by type (likes / replies / reposts / mentions).
SendingdeferredOutgoing webmentions aren't wired, so a Like that responds to another post won't notify it at Phase 3a. This is the primary reason the h-entry nesting issue (§5) is accepted for v1.

h-entry nesting (§5). The only h-entry in the layout will be the hidden authorship block; the visible u-like-of anchor and .e-content will sit outside it, so a strict parser won't tie the like property to the entry. Harmless while sending is off; fix it when the sending side of the milestone lands — see §5 and §14.
