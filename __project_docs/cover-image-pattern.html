Build-time cover images

Locked 23 May 2026 · live in reading / watching / jam · planned for all five Phase 3b heavy types · extracted from live code 23 May 2026

One hero image per post — a book cover, a film poster, album art, a photo, an episode artwork — is handled the same way across every image-led post type: store its URL or path in a cover: frontmatter field, render it as a plain <img>, and let the always-on Eleventy Image HTML Transform fetch (if it's remote), optimize, and self-host it at build time. This page is the canonical write-up; the per-type specs (Reading §6/§12, Watching §6/§13, Jam §6/§12) link here instead of repeating the mechanism.

Locked decision, not a proposal. This convention was settled 23 May 2026 (recorded in ROADMAP.md "Locked decisions" and __design/Reference - cover image pattern.md). It replaced an earlier plan to download covers into per-post page bundles via a normalize-posts.js / colocate-cover.js script — that apparatus was dropped, never built, because the build already self-hosts remote images and the script was redundant. If you find a spec still describing co-located covers or a coverSource: field, it predates this decision. Re-evaluated 25 May 2026 — declined, decision re-confirmed. Bundling the cover next to the .md was reconsidered; the motivation was organizational tidiness, not a functional gap. It was declined because the Obsidian Web Clipper cannot download a cover: image (it writes only frontmatter + body text, and local-images-plus pulls down body images, never a frontmatter cover), so “always bundled” would require reviving the dropped script or a manual step per clip — for a benefit the build already delivers (the deployed site self-hosts every cover; a dead URL degrades to a placeholder, not a broken build). The sanctioned per-post alternative is the local-cover escape hatch (§7).

1. The discovery — two image paths, opposite on a remote URL

JEDEE has two ways to turn an image reference into optimized output, and they behave oppositely on a remote URL. The discovery (made while fixing the Watching/Letterboxd poster bug, commit ae78277) is that a plain <img src="https://…"> is the way to pull a remote image into the build.

 {% image %} / {% imageKeys %} shortcodeEleventy Image HTML Transform
Defined insrc/_config/shortcodes/image.js (Lene's upstream EE code)eleventy.config.js:79-92 (eleventyImageTransformPlugin)
Triggered byAn explicit shortcode call in a templateAny plain <img src="…"> in the rendered output HTML
Remote URLBreaks the build — see belowFetched, optimized, self-hosted
Local pathYes (its only mode)Yes
Outputdist/assets/images/<name>-<w>.{avif,webp,jpeg}dist/<page-path>/<hash>-<w>.{webp,jpeg}

Why the shortcode breaks on a remote URL. image.js:37 unconditionally prepends ./src to any source that doesn't already start with it:

if (!src.startsWith('./src')) { src = `./src${src}`; }

A remote URL becomes the nonsense path ./srchttps://…, and eleventy-img then stats it as a local file → ENOENT → build fails. (Verified by renaming cover: → image: on a watching post and building.)

How the transform self-hosts a remote URL. The transform post-processes every <img> in the output HTML. For a remote src it fetches the file (via @11ty/eleventy-img, which uses @11ty/eleventy-fetch to cache), resizes, writes the variants next to the page, and rewrites src to the local path plus <source>/width/height. So the hot-linked URL never reaches the final output — the image is self-hosted and optimized.

2. The canonical pattern

Store the single hero image in a cover: field and render it as a plain <img>:

{% if cover %}
  <img eleventy:optional="placeholder" src="{{ cover | safe }}" alt="…" loading="lazy">
{% endif %}

Live in src/_layouts/{reading,watching,jam}.njk (the detail page, capped to max-inline-size: 14rem) and src/_includes/partials/card-{reading,watching,jam}.njk (the archive cards). The same plain-<img> handles a local cover too (the transform resolves local paths as well), so it's one code path for both remote and local sources.

Never route a cover through {% image %}. A remote URL breaks the build (§1); a local path would work, but mixing the two paths per source type invites the exact image:-vs-cover: field confusion this convention removes. Covers always use the plain <img>.

3. Two non-negotiables (each can fail the build)

RuleWhy
| safe on the srcNunjucks escapes & → &amp;; the transform then fetches the mangled multi-param URL → 404 → fatal build. | safe keeps the raw URL intact (the transform replaces the <img>, so the raw URL never reaches output). Watching only worked before by luck — its single-param Letterboxd URL had no & to escape; a Google Books cover (many params) hits it immediately.
eleventy:optional="placeholder"A 404 cover hard-fails the build by default (exit 1, page not written) — verified. With this attribute a dead cover degrades to a transparent placeholder, the build completes (exit 0), and the 404 is logged as a warning. (eleventy-img v6; global failOnError stays true, so genuine local/article image typos still fail loudly.)

4. One hero vs. many body images — keep them distinct

This convention is only for the single hero/cover. Multiple co-located body or gallery images are a different need with a different mechanism.

NeedMechanism
(a) Single hero / cover (remote or local)This pattern — cover: + plain <img>
(b) Co-located body / gallery images (multiple)Page-bundle layout + markdown / {% image %} (and gallery.njk for a lightbox)

Photo's opt-in gallery is (b); its lead photo is (a). Don't let the cover pattern bleed into galleries, and don't let the page-bundle gallery story bleed back into covers. Covers stay flat files; bundles are opt-in, only when a post has genuine co-located body images (handled by the local-images-plus Obsidian plugin at authoring time).

6. Where it applies

  • Live today: reading, watching, jam — one cover: field each, rendered in both the layout and a bespoke card (commit d9dd086).
  • Phase 3b (planned), all five: Photo, Recipe, Event, Audio (cover art), Video (poster). Each reuses this pattern for its single hero. For Photo/Recipe a local lead photo may instead use {% image %} (it carries u-photo via the shortcode's imageClass param) — the plain-<img> is what a remote hero needs.
  • Light types (Phase 3a, shipped): none use it. card-response.njk has no image slot by design. Bookmark is the only plausible opt-in (a preview / og:image / favicon of the bookmarked page) — a future design choice, not wired.
  • article / note: their hero goes through entry-header.njk → imageKeys (the shortcode, local-only). A remote hero there would break — that's the one place this pattern doesn't reach, and the case Option C (§8) would unlock.

7. Caveats

  • Build-time network dependency. On a cache miss the build must reach the remote host; offline/CI builds rely on the eleventy-fetch cache. A cold cache with no network stalls or fails.
  • Cache duration is the plugin default. No cacheOptions: { duration } is set on the transform yet (eleventy.config.js:79-92). Set one for resilience against refetch and link-rot — a deferred optional pass, not v1.
  • dist/ is gitignored — covers are refetched each build. The localized image files are regenerated every build, not committed, so the deployed site is a self-contained archive of its covers but the source repo is not. Per-post archival escape hatch: for any single post you want permanently bundled, download its cover into src/assets/images/reading/ and point cover: at that local path — exactly as The Kingdom of God is Within You.md does (cover: /assets/images/reading/…-cover.jpg). It renders through the identical plain-<img> path, is committed to git, and adds no machinery. This is the sanctioned alternative to automatic bundling (declined 25 May 2026 — see the locked-decision note above). Jam ×2 and that Reading post already use it.
  • Detail-page placeholder is invisible. A placeholder has no width/height, so it produces no box on the detail page. Cards get a clean box via aspect-ratio CSS (custom-card[data-poster] img { aspect-ratio: 2/3 } in src/assets/css/local/custom-card.css); a one-line min-block-size on the detail <img> would give it a visible box if wanted.

8. Option C — remote-aware shortcode (DEFERRED until after Phase 3b)

The broader alternative is to make the {% image %} shortcode remote-aware so the image: field accepts remote URLs too — the shortcode's only incompatibility is the ./src prepend (§1), which a one-line guard could skip for ^https?://. @11ty/eleventy-img already fetches + caches remote URLs natively, so the rest would just work.

It earns its keep only for the article / note hero via entry-header.njk — the one place a remote image is otherwise impossible (§6). A complete version is more than one line (remote filename hashing in filenameFormat; a try/catch for 404 resilience to match eleventy:optional), and — decisively — image.js is Lene Saile's upstream Eleventy Excellent code, so patching it in place invites merge friction on future EE syncs.

Decision (23 May 2026): defer. The heavy types all ship fine on the plain-<img> pattern; Option C is optional polish. If ever adopted, prefer a thin JEDEE-specific wrapper shortcode (or an upstream PR to Lene) over editing image.js directly. Until then, the plain-<img> pattern keeps the divergence confined to JEDEE's own templates, where it belongs.
