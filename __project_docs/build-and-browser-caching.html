Build & browser caching

Reference · written 23 Jun 2026 · facts verified against the live site (johanedlund.se) and a production build · no code change

The word cache shows up three times on JEDEE, meaning three different things in three different places. They are easy to conflate. This doc keeps them apart: a build cache that only speeds up deploys, the ordinary browser cache that every visitor's browser keeps, and the service-worker cache that the PWA layer adds on top. The third already has its own doc — this one covers the first two and shows where the third fits.

A cache is simply a stored copy of something, kept so it doesn't have to be fetched or rebuilt next time. The three layers below differ only in who keeps the copy and who benefits — the build server, the visitor's browser, or the installed app.

1. Three caching layers

Two of the three never touch a visitor. The build cache lives on Netlify's build server and only makes the next deploy faster. The browser cache and the service-worker cache both live on the visitor's device. The diagram separates them by who sees each one.

LayerLives onSpeeds upBusted by
Build cacheNetlify's build serverThe next deploy.Nothing automatic — it just grows; safe to clear by hand.
Browser cacheThe visitor's browserRepeat visits.A changed URL, or ETag revalidation (§3).
Service-worker cacheThe visitor's browser (PWA)Offline + repeat visits.Each deploy wipes it (see the PWA caching doc).

2. The build cache

When Netlify builds the site it fetches a handful of things from the open web. Re-fetching all of them on every deploy would be slow and rude to those servers, so the downloads are stored in a folder called .cache/ and carried over from one deploy to the next. This is the only reason it exists; it never ships to a visitor.

The carry-over is done by one Netlify plugin, declared at the top of netlify.toml:

[[plugins]]
package = "netlify-plugin-cache"
  [plugins.inputs]
  paths = [ ".cache" ]

Without it, every deploy would re-download every remote thing below. .cache/ is the store used by @11ty/eleventy-fetch — Eleventy's helper for "fetch this once and remember it." Three build steps fill it:

What's cachedFetched byWhy
Remote cover imagesThe eleventy-img HTML Transform (uses eleventy-fetch under the hood)Each remote cover: URL is downloaded and self-hosted at build. Full story: Build-time cover images.
Webmentionssrc/_data/webmentions.js (eleventy-fetch, directly)Pulls replies/likes from webmention.io so they can be rendered into the page at build.
Photo static mapsThe same image transform, from a Geoapify URL built in partials/photo-map.njkA small map image per photo post. The request URL carries MAP_API_KEY (from src/_data/meta.js).

Why the build cache is excluded from secret scanning. The Geoapify map URL has the API key baked into it, and eleventy-fetch stores the URL verbatim under .cache/. Netlify scans build-generated files for leaked secrets, so netlify.toml tells it to skip the cache:

[build.environment]
  SECRETS_SCAN_OMIT_PATHS = ".cache/**"

This is safe because the cache is not deployed — only dist/ ships, and the deployed output never contains the key. The key itself lives in the Netlify UI (Builds scope), never in the committed netlify.toml. If a deploy is mysteriously slow, the first thing to check is whether the build log says it restored this cache.

3. The browser cache

This is the cache people mean by "the cache" — the copies a visitor's browser keeps so a second visit doesn't re-download everything. The browser decides what to keep from the Cache-Control header on each response, and whether a kept copy is still current using its ETag (a content fingerprint). On JEDEE those headers come entirely from netlify.toml; there is no _headers file.

Only two kinds of file get a long cache. Everything else falls to Netlify's default, which is "keep a copy, but check with the server every time before using it." The values below were read live off johanedlund.se on 23 Jun 2026.

ResourceCache-ControlSet by
Fonts — *.woff2max-age=31536000, public, must-revalidate (1 year)netlify.toml
Component scripts — /assets/scripts/components/*.jsmax-age=31536000, public, must-revalidate (1 year)netlify.toml
HTML pagespublic, max-age=0, must-revalidate + ETagNetlify default
Images, favicon, feed.json, everything elsepublic, max-age=0, must-revalidate + ETagNetlify default

max-age=0, must-revalidate sounds like "don't cache," but it isn't — the browser keeps the copy and revalidates it cheaply: it sends the ETag back and the server answers 304 Not Modified (no body) if nothing changed, or 200 with the new copy if it did. So unchanged pages and images cost a tiny round-trip, not a full download. The 1-year files skip even that round-trip until the year is up.

Every response also carries the security headers from the for = "/*" block (Content-Security-Policy: upgrade-insecure-requests, X-Content-Type-Options, X-Frame-Options, a locked-down Permissions-Policy, and so on). That block sets no Cache-Control — caching and security are configured independently.

4. Cache-busting — by inlining, not by filename

"Cache-busting" is the trick of making sure a visitor never gets a stale copy of changed code. Many sites do it by putting a content fingerprint in the filename — style.a1b2c3.css — so the URL changes whenever the content does. JEDEE's CSS and JavaScript reach that same guarantee a simpler way: they ride inside the HTML.

In a production build, src/_includes/head/css-inline.njk inlines the whole stylesheet into every page as a <style> block, and the site's own JavaScript is inlined as <script> blocks. There is no separate CSS file request at all. Since the HTML itself is served max-age=0, must-revalidate (§3), every visit revalidates the page — and the CSS and JS, being part of that page, are revalidated with it. A code change ships on the next deploy with zero chance of a stale stylesheet.

The /bundle/<hash>.css path is dev-only. Eleventy's bundle plugin (eleventy.config.js:100, addBundle('css', { hoist: true })) can emit content-hashed /bundle/<hash>.css files, and it does — but only when you run npm start. In that mode css-inline.njk links those files (so a browser refresh picks up edits without a full reload). The production branch inlines instead, so a production build emits no /bundle/ directory and no page links one. If you ever expected a [[headers]] rule for /bundle/*, that's why there isn't one — there is nothing at that path to cache in production.

The CSS and JS are assembled by two build steps before being inlined: src/_config/events/build-css.js runs the PostCSS pipeline over the global/ tree, and src/_config/events/build-js.js bundles the JavaScript with esbuild. The npm run build command wipes the previous output first (npm run clean = rimraf dist src/_includes/css src/_includes/scripts), so each build is from scratch.

Worth knowing — the long-cached files use stable names, not hashes. The only resources with a 1-year cache (the *.woff2 fonts and the /assets/scripts/components/*.js component scripts) keep the same filename across deploys. Fonts effectively never change, so that's free. A component script changing within a returning visitor's cached year is the one case where a hashed filename would help — but must-revalidate means the browser can't serve it stale past the year, and PWA visitors get a clean cache on every deploy (the SW cache is per-build; see the PWA doc). It's a minor, EE-stock trade-off, not a bug — flagged here so a future reader isn't surprised by it.

5. Reference files

  • netlify.toml — the netlify-plugin-cache block (build cache), the three [[headers]] blocks (browser cache + security), and SECRETS_SCAN_OMIT_PATHS.
  • .nvmrc — the only source of the build's Node version (currently 22); not netlify.toml, not package.json.
  • src/_includes/head/css-inline.njk — the inline-in-production / link-in-dev switch (§4).
  • eleventy.config.js:100 — addBundle('css', …), the source of the dev-only /bundle/<hash> paths.
  • src/_config/events/build-css.js + build-js.js — the PostCSS and esbuild steps that produce the inlined CSS/JS.
  • src/_data/webmentions.js — the one direct eleventy-fetch consumer (build cache).
  • src/_includes/partials/photo-map.njk + src/_data/meta.js — the Geoapify static-map URL that makes the secret-scan exclusion necessary.
