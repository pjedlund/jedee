post-type spec

RSVP

Planned · Phase 3a · singular rsvp / plural rsvps · derived from the Phase 3 plan 22 May 2026

An RSVP is a short post responding to an event with an attendance declaration — yes, no, maybe, or interested. It is the IndieWeb's structured reply to an event URL, carrying both a u-in-reply-to target (the event) and a p-rsvp value (the answer). One of the five light "response" types in Phase 3a.

1. Singular / plural identity

RSVP is asymmetric: the type is singular, the URL namespace is plural. The Eleventy collection will be named with the singular (collections.rsvp), but the folder, URL, archive, and feed will all use the plural.

2. Naming & aliases

JEDEE's event-response type is named RSVP (singular) / RSVPs (plural), following IndieWeb convention. The name derives from the French Répondez s'il vous plaît ("please reply") — conventionally used for event attendance responses. The IndieWeb rsvp post type maps directly to this: a reply to an event URL that carries a structured attendance value.

TermStatusWhere it appears / why
rsvp / rsvpschosen nameType, layout, collection, URL, archive, feed, nav (see §1).
rsvpIndieWeb verb — maps directlyUnlike Jam (which maps to "listen"), RSVP is its own IndieWeb post type. The µf2 properties are u-in-reply-to (the event URL) + p-rsvp (the attendance value). See §5.
inReplyTocamelCase URL field — LOCKEDTop-level frontmatter key naming the event URL. camelCase because Nunjucks cannot read hyphenated top-level keys (in-reply-to would parse as subtraction). The IndieWeb semantic lives in the µf2 class on the rendered element, not the field name. See §4.

4. Frontmatter (planned)

The planned per-post frontmatter shape. Nothing is extracted from live code — this type has no code yet. category, layout, and permalink will come from the folder data file src/posts/rsvps/rsvps.json and are not authored per-post.

---
title: RSVP to IndieWebCamp Berlin 2026         # optional; title-optional type
inReplyTo: https://events.indieweb.org/...      # required — the event URL → u-in-reply-to
rsvp: yes                                       # required — one of: yes | no | maybe | interested
date: 2026-05-22T10:00:00+01:00                 # required — post timestamp

draft: false                                    # optional

  - indieweb
---

category, layout, and permalink are not authored per-post — the plan specifies they will come from the folder data file src/posts/rsvps/rsvps.json, which will set { "layout": "rsvp", "tags": "posts", "category": "rsvp", "permalink": "/rsvps/{{ page.fileSlug | slugify }}/index.html" }. The folder data file also sets tags: "posts" (the system tag) so RSVPs appear in the global posts collection; this is separate from per-post topic tags.

5. Microformats (µf2)

The layout will emit a visible anchor for the event target (u-in-reply-to) and a <data> element for the attendance value (p-rsvp). The plan specifies the following planned layout body:

<p>RSVP <a class="u-in-reply-to" href="{{ inReplyTo }}">{{ inReplyTo }}</a></p>
<data class="p-rsvp" value="{{ rsvp }}">RSVP: {{ rsvp }}</data>
<div class="e-content">{{ content | safe }}</div>

Visible target, not hidden data. The u-in-reply-to target uses a visible <a> (µf2 class on the <a>), not a <data hidden> element. RSVP posts are often body-less — the target event link is the content, so it must be visible. Contrast Jam, which uses a hidden <data class="u-listen-of"> because Jams always carry a body. The p-rsvp value does use a <data> element, but the event target link is always visible.

PropertyClassFrom
Event targetu-in-reply-toinReplyTo (on a visible <a>)
Attendance valuep-rsvprsvp (on a <data> element)
Bodye-contentpost content (optional — post may have no body)
Publisheddt-publisheddate (via entry-header → date.njk)

h-entry nesting caveat (DEFERRED — v1): cloning note.njk puts the visible u-in-reply-to anchor, the p-rsvp value, and .e-content outside the only h-entry in the layout (the hidden authorship block), so a strict mf2 parser will not tie these properties to the entry. Accepted for v1 because webmention sending is not wired up yet. Flagged in the plan's Decisions and slated for the webmention milestone — either give RSVP a proper self-contained h-entry, or restructure note.njk and the shared chrome (the latter also fixes the existing types). See §13.

8. Feed

RSVP has a feed (plan table: Feed ✅). A pair of templates will be created by cloning src/feeds/notes.json.njk + notes.xml.njk to src/feeds/rsvps.json.njk + src/feeds/rsvps.xml.njk. The plan stresses updating the permalink: frontmatter immediately — leaving the cloned permalink: /notes/feed.xml intact would collide with the Notes feed and error the build.

# rsvps.xml.njk
permalink: /rsvps/feed.xml
feedCollection = collections.rsvp
feedTitle = "RSVPs"
feedDescription = "Events I'm RSVPing to."
feedSelfUrl = "/rsvps/feed.xml"
→ includes feeds/atom-body.njk

# rsvps.json.njk — same vars, with:
permalink: /rsvps/feed.json
feedSelfUrl = "/rsvps/feed.json"
→ includes feeds/json-body.njk

The permalink: frontmatter (not the filename) controls the output path.

Title-less entry wrinkle (OPEN): RSVP is title-optional (plan Decision 9). Title-less entries produce an empty <title> element in the Atom feed. The plan flags this as open: the options are (a) compute a fallback title (e.g. "RSVP to <host>") or (b) accept an empty <title> for v1. No decision has been made.

12. Collection registration (wiring)

The plan's Step 0 introduces a POST_TYPES array refactor before any Phase 3a type is added. The planned wiring is:

// src/_config/collections.js  (after the Step 0 refactor)
export const byCategory = cat => collection =>
  collection.getFilteredByGlob('./src/posts/**/*.md')
    .filter(item => item.data.category === cat)
    .reverse();

export const POST_TYPES = [
  'article', 'note', 'reading', 'jam', 'watching',
  // Phase 3a additions — rsvp added here:
  'bookmark', 'reply', 'rsvp', 'like', 'repost'
];

// eleventy.config.js  (after the Step 0 refactor)
import { POST_TYPES, byCategory, showInSitemap, tagList } from './src/_config/collections.js';

// collection loop (covers rsvp automatically):
POST_TYPES.forEach(t => eleventyConfig.addCollection(t, byCategory(t)));

// layout alias — EXPLICIT, not looped (see note):
eleventyConfig.addLayoutAlias('rsvp', 'rsvp.njk');

Why layout aliases stay explicit. The plan locks this: POST_TYPES includes article, which has no article.njk (it uses layout: post). Looping aliases over POST_TYPES would emit a bogus addLayoutAlias('article','article.njk'). Every layout alias is therefore added explicitly per type alongside the shipped aliases. The POST_TYPES.forEach loop only wires addCollection.

Category names never enter tags, so "rsvp" does not pollute /tags/.

13. Webmentions

Nothing here is RSVP-specific — the plumbing is shared by every post type and RSVP will inherit it through the base layout and entry-footer.njk. Discovery is shipped; receiving and sending are deferred to the webmention milestone.

Authorship h-cardwill be shipped (inherited from note.njk clone)The hidden h-entry block in rsvp.njk will carry u-url, p-name u-url rel="author", and a u-author h-card avatar so a receiver can attribute the post (§5).
Render slotwill be wired, no-oprsvp.njk → entry-footer.njk → partials/webmentions.njk, currently an empty stub — safe to call while the renderer is empty.
Receiving / renderingdeferredThe webmention milestone wires a webmention.io fetch (via @11ty/eleventy-fetch, ~24 h cache); webmentions.njk then groups received mentions by type (likes / replies / reposts / mentions).
SendingdeferredOutgoing webmentions aren't wired, so a published RSVP will not notify the event host yet.

h-entry nesting (§5). The only h-entry in the layout will be the hidden authorship block; the visible u-in-reply-to anchor, the p-rsvp value, and .e-content will sit outside it, so a strict parser won't tie these properties to the entry. Harmless while sending is off; fix it when the sending side of the webmention milestone lands — see §5 and §14.
