Jam

Shipped · Phase 2 · singular jam / plural jams · extracted from live code 22 May 2026

A Jam is a short post sharing music (or other audio) the author is listening to — an album, track, or release, usually linking out to Bandcamp or a streaming service. An IndieWeb "listen" post.

1. Singular / plural identity

Jam is asymmetric: the type is singular, the URL namespace is plural. The Eleventy collection is named with the singular (collections.jam), but the folder, URL, archive, and feed all use the plural.

Note the mismatch: the folder is jams/ but its data file sets category: "jam", and the collection registered from that category is jam (singular). Don't "fix" this — the layout alias, collection, and category are all singular by design.

2. Naming & aliases

JEDEE's music type is named Jam (singular) / Jams (plural), after This Is My Jam — a curated endorsement, not a passive scrobble of whatever happened to be playing. Chosen deliberately over symmetry with reading / watching because the word carries the endorsement.

TermStatusWhere it appears / why
jam / jamschosen nameType, layout, collection, URL, archive, feed, nav (see §1).
listenIndieWeb verb — kept in µf2 + schemaThere is no "jam" microformat: the property is u-listen-of and the planned schema is ListenAction. Jam reuses IndieWeb's listen vocabulary.
listeningprevious name + asset pathThe folder was src/posts/listening/ until Phase 2 renamed it to jams/. The earlier /listening/* /jams/:splat 301 redirect has been removed, freeing the /listening/ namespace for a possible future Listen type (see note). Album art still lives under /assets/images/listening/.
musictopic tagEvery sample carries tags: [music] — a user-facing tag, not the category.

Listen vs. Jam: IndieWeb splits Listen (passive scrobbles — whatever's playing) from Jam (curated picks). If a scrobble feed ever lands it would be a separate Listen type at /listening/, not a rename of Jam.

Cover field: the image: field was renamed to cover: (commit d9dd086). It can hold a local path (as in the sample) or a remote URL; either way the Eleventy Image HTML Transform optimizes/fetches and self-hosts it at build. Covers stay flat — the earlier plan to co-locate cover: ./cover.<ext> in a page bundle with a coverSource: field was dropped (23 May 2026). See §12 and build-time cover images.

Canonical vs. live drift

The original spec's canonical names (listen-of, albumArt, year, favoriteTrack, genre[], dateListened) differ from what the live importer emits (source ≈ listen-of, cover [was image] ≈ albumArt, released ≈ year). Resolution decision (D2): tighten the canonical names but let the Clipper layer emit them; existing samples stay as-is, not migrated.

6. Card

Jam has a bespoke album-art-led card: src/_includes/partials/card-jam.njk (set in jams.njk: cardPartial = "card-jam.njk"). Built in commit d9dd086, it replaced the shared card-blog.njk so the album art could render from cover (the shared card reads item.data.image, which Jam no longer sets). It mirrors card-watching.njk.

12. Cover image & page bundles

The album art is handled by the project-wide build-time cover pattern: the cover: field holds a local path or a remote URL, the layout and card render it as a plain <img eleventy:optional="placeholder" src="{{ cover | safe }}">, and the Eleventy Image HTML Transform optimizes (local) or fetches + optimizes (remote) and self-hosts it at build. Jams stay flat .md files with the cover under /assets/images/listening/ (or a remote URL) — no page bundle is needed for the cover.

The page-bundle / co-located-cover plan was dropped (23 May 2026). An earlier Clipper-era plan made each Jam a page bundle holding cover: ./cover.<ext> plus a coverSource: origin field, with a colocate-covers.js / normalize-posts.js script to download remote art into the bundle. That apparatus was never built: the build-time transform already self-hosts the remote cover, so the download-and-commit step was redundant. The coverSource: field and the colocate script do not exist.

AspectWas planned (Clipper-era — dropped)Locked (shipped)
Post filepage bundle src/posts/jams/<slug>/<slug>.mdflat src/posts/jams/<slug>.md
Cover storageco-located cover.<ext> downloaded into the bundleremote URL, or /assets/images/listening/<file>; self-hosted at build
Frontmattercover: ./cover.<ext> + coverSource:single cover: (URL or path)
How it landsa colocate / normalize script downloads + commits the filethe HTML Transform fetches/optimizes at build; nothing committed (dist/ is gitignored)

Page bundles themselves remain available (Eleventy Excellent's <folder>/<folder-name>.md convention) for any genuine co-located body assets a Jam might gain — they're just no longer the mechanism for the cover.

13. Collection registration (wiring)

// src/_config/collections.js
const byCategory = cat => collection =>
  collection.getFilteredByGlob('./src/posts/**/*.md')
    .filter(item => item.data.category === cat)
    .reverse();
export const jam = byCategory('jam');

// eleventy.config.js
import { ... jam ... } from './src/_config/collections.js';
eleventyConfig.addLayoutAlias('jam', 'jam.njk');
eleventyConfig.addCollection('jam', jam);

Category names never enter tags, so "jam" does not pollute /tags/.

14. Authoring — Web Clipper + plugin setup

The intended authoring path for a Jam is "right-click a Bandcamp album page → save to the vault." The Obsidian Web Clipper (browser extension) reads the page's MusicAlbum JSON-LD through a per-source template and writes a shape-correct .md flat into src/posts/jams/ (like the shipped Letterboxd clipper — Watching §13). The cover property holds the remote album-art URL, which the build-time HTML Transform self-hosts; nothing is downloaded into the vault (§12). No per-post manual frontmatter typing.

Planned. The Bandcamp template (_resources/bandcamp-clipper.json) is not authored yet. Below is the structure-first scaffold: every relevant Jam field is present and mapped to a Clipper source, but the selectors have not been verified against live Bandcamp markup (that verification is a follow-up). It is modeled on the one working precedent, _resources/letterboxd-clipper.json (Watching).

Bandcamp Clipper template — scaffold

    { "name": "listen-of",   "value": "{{url}}",                                            "type": "text" },
    { "name": "year",        "value": "{{schema:@MusicAlbum:datePublished|date:\"YYYY\"}}", "type": "number" },
    { "name": "date",        "value": "{{date}}",                                           "type": "text" },

Field → source mapping

The template emits the canonical forward shape (per §4's "Canonical vs. live drift" note and decision D2): listen-of, year, and cover rather than the live samples' source, released, and image. Existing samples are not migrated — the Clipper layer emits the canonical names going forward, and the normalize step reconciles the rest (§12).

Obsidian plugin setup

One vault-side community plugin completes the authoring flow:

PluginRoleRequired settings
obsidian-local-images-plus (installed)Downloads body images — markdown ![](URL), <img src>, base64 — into a folder named after the note. Automatic, MD5-named, idempotent. Does not touch YAML frontmatter.Automatic mode on; placement "next to note in a folder named after the note."

Division of labor. The Clipper writes the flat .md (frontmatter plus an empty body). It does not download images — and it no longer needs to: the cover stays a remote URL and the build-time HTML Transform self-hosts it at build (§12). The dropped normalize / colocate step is therefore unnecessary — there is no per-clip cover download and no backfill. Demoting the cover into the body to let a plugin grab it was rejected — covers are data for cards / OG / JSON-LD, not body content. obsidian-local-images-plus still handles a genuine body image (e.g. an inline album-art <img> inside a clip), but is a no-op for the typical Jam clip.

15. Micropub (forward-compat — endpoint deferred)

JEDEE has no Micropub endpoint today, and building one is its own milestone — sequenced after Phase 4 (see ROADMAP.md and __design/Plan - Phase 3 (10 new post types) - final.md). This section is forward-compat documentation only: it records why the Jam type is already shaped so a future endpoint drops in without a retrofit. No code; nothing to build here.

A Micropub create request for a Jam is a listen post. Three properties of the existing design — none added for Micropub — make the endpoint a thin write path rather than a new data model:

Forward-compat moveHow Jam already satisfies itSee
Micropub-aware propertyA create request carries listen-of (the listened-to URL) — the same canonical property the Clipper emits, rendered as u-listen-of. The endpoint writes the same fields the Clipper does, so the layout never branches by source.§5, §14
No cover-download contract neededBecause covers are self-hosted at build (§12), neither the Clipper nor a future Micropub endpoint downloads images — both just write a cover: URL. The earlier shared colocate-cover.js library was dropped (23 May 2026); there is no per-path image-download code to share.§12
Flat write path (bundle only for body media)A future endpoint writes a Jam as a flat posts/jams/<slug>.md with a cover: URL — the same shape the Clipper produces. Only a clip carrying genuine co-located body media would use a page bundle (saving uploads alongside as photo-N.<ext>); the cover never drives bundling.§12

One shape, two producers. The frontmatter the Clipper writes and the payload a future Micropub client would send are the same shape, so adding the endpoint introduces no new field mapping. With covers self-hosted at build and Jams written flat (§12), there is no bundle-creation or normalize step to reconcile — the old §17 divergence over "who creates the bundle" is moot.

Status: planned, no code — like page bundles (§12) and the Web Clipper template (§14). The endpoint is a separate milestone after Phase 4; this section exists so the forward-compat story is discoverable from the spec.

16. Webmentions

Webmention is the IndieWeb's federated response protocol: likes, replies, and reposts from other sites arrive as cross-site comments. Nothing here is Jam-specific — the plumbing is shared by every post type and Jam inherits it through the base layout and entry-footer.njk. Discovery is shipped; receiving and sending are deferred to the webmention milestone.

PieceStateWhere
Endpoint discoveryshipped (Phase 1)<link rel="webmention" href="https://webmention.io/johanedlund.se/webmention"> in <head> via src/_includes/head/meta-info.njk (jam uses layout: base).
Authorship h-cardshippedThe hidden h-entry block in jam.njk carries u-url, p-name u-url rel="author", and a u-author h-card avatar so a receiver can attribute the post (§5).
Render slotwired, no-opjam.njk → entry-footer.njk → partials/webmentions.njk, currently an empty stub — safe to call while the renderer is empty.
Receiving / renderingdeferredThe webmention milestone wires a webmention.io fetch (via @11ty/eleventy-fetch, ~24 h cache); webmentions.njk then groups received mentions by type (likes / replies / reposts / mentions).
SendingdeferredOutgoing webmentions aren't wired, so a Jam that responds to another post doesn't notify it yet.

h-entry nesting (§5). The only h-entry in the layout is the hidden authorship block; the visible u-listen-of + .e-content sit outside it, so a strict parser won't tie the listen target to the entry. Harmless while sending is off; fix it when the sending side of the milestone lands — see §5 and §17.

17. Status & open items

  • Shipped in Phase 2 — layout, archive, feed, nav, and 2 sample posts all live.
  • Field drift (canonical vs importer names) — normalization deferred to the Clipper layer, not a migration. The canonical forward shape is what the planned Bandcamp Clipper template emits (see §14).
  • odeslico — authored but unrendered. The Clipper layer plans to retire it in favor of syndication[] (see §14); existing samples keep odeslico until normalized. (open)
  • Webmentions — discovery + the no-op render slot are shipped; receiving/rendering, sending, and the h-entry nesting fix (§5) are deferred to the webmention milestone. See §16.
  • Schema upgrade BlogPosting → ListenAction — Phase 4.
  • Page bundles / co-located covers — dropped (23 May 2026). Covers are self-hosted at build via the plain-<img> transform (cover convention); Jams stay flat. Page bundles remain available for genuine body assets only. See §12.
  • Dedicated card — DONE (commit d9dd086). card-jam.njk is the album-art-led card (§6), modeled on card-watching.njk. Reading and Watching also have bespoke cards now; card-blog.njk stays the Article/Note-style shared card.
  • Authoring (Web Clipper) — the Bandcamp Clipper template and local-images-plus setup are documented in §14; the template JSON itself (_resources/bandcamp-clipper.json) is planned, not yet authored. (open)
  • Micropub endpoint — forward-compat only; the Jam shape is already endpoint-ready (§15). The endpoint itself is a separate milestone after Phase 4, not yet built. (open)
  • Bundle creation — RESOLVED: flat, no bundle. Dropping cover co-location (§12) settles the old §12-vs-§14 divergence: the Clipper writes a flat .md (matching the Letterboxd precedent), there is no normalize-posts promotion step, and the cover is self-hosted at build. Bundles are opt-in for genuine body assets only.
