post-type spec

Video

Planned · Phase 3b · singular video / plural videos · designed from the Phase 3 plan 22 May 2026

A Video post is a video publication — a self-hosted clip the author owns, or a hosted embed (YouTube, PeerTube). Its primary content is the moving image. Video is the second of the two creator-side, hosted-media types (with Audio) and the 15th type overall (the locked "accept 15 types" decision). The two are designed together because they share the enclosure derivation, the RSS 2.0 media feed, and the bespoke media-led card; Video adds a provider discriminator so a single type covers both self-hosted files and hosted embeds.

Provenance. Audio + Video are the second heavy Phase 3b increment (after Photo), designed together in one pass. The Phase 3 plan only outlines Video (self-hosted / embedded video; u-video µf2 + <video>/embed in the layout; enclosure-shaped feed mirroring Audio; schema VideoPosting embedding VideoObject). The discriminator shape, the embed-vs-enclosure feed rule, and the build-vs-defer calls below are decisions of the 22 May 2026 design increment (_generated/Plan - Audio + Video post types (Phase 3b design).md), built on the plan — not invented to fill the page. "The plan specifies …" means the Phase 3 plan; "the design increment decides …" means the 22 May pass. Mechanisms that do not exist yet (the enclosure filter, the RSS 2.0 podcast/vodcast body, the VideoObject schema) are marked to-build; the YouTube/PeerTube embed components, by contrast, already ship and are reused as-is.

1. Identity

Video is asymmetric like the shipped types and Photo: the type is singular, the URL namespace is plural. (Its sibling Audio is the symmetric exception — "audio" has no plural.) The collection is named with the singular (collections.video); the folder, URL, archive, and feed use the plural videos.

4. Frontmatter (planned)

The shape below is the planned authoring surface decided by the 22 May design increment. No sample file exists yet. category, layout, and permalink come from the folder data file src/posts/videos/videos.json (see §1, §14). The video object carries a provider discriminator; the other fields depend on which provider is set.

Co-located media needs passthrough wiring (file provider). Like Audio's audio file, a self-hosted video.src is not processed by Eleventy Image; for the <video src> and the enclosure URL to resolve, the co-located file must be passthrough-copied to dist/. Not wired today — flagged as a build prerequisite. (The poster image is handled by the image shortcode.) (to-build)

5. Microformats (µf2)

The layout will be src/_layouts/video.njk (planned), modeled on watching.njk. For a self-hosted video, u-video goes on the visible <video> element:

{# planned — file provider #}
<video class="u-video" controls preload="metadata"
       poster="{{ video.poster }}" src="{{ video.src }}"></video>
PropertyClassFrom
Video (file only)u-video (on the <video>)video.src
Bodye-contentpost content (may be empty)
Publisheddt-publisheddate (via entry-header → date.njk)
Authorshiph-entry / h-card / u-authorhidden block, meta.author

Embeds carry no u-video — an honest µf2 limitation. u-video is meant to point at a video file URL. A YouTube/PeerTube embed exposes no such file — only a watch page and an iframe. So embed entries do not emit u-video; they render the player plus the component's built-in <custom-youtube-link> / <custom-peertube-link> watch-link fallback. A consumer reads the embed as a linked video, not a u-video property. This is a known gap of the embed path, not a defect to paper over. (documented limitation)

h-entry nesting caveat — DEFERRED. Modeling on watching.njk puts the visible video and .e-content outside the only h-entry (the hidden authorship block), so a strict mf2 parser won't tie the video to the entry. Accepted for v1 (webmention sending not wired). Fix in the webmention milestone. Same caveat as every other type.

6. Media providers — the layout switch

One type, three rendering paths, selected by video.provider. The two embed paths reuse existing WebC components — no new embed code. This works inside a Nunjucks layout because EE registers the WebC plugin with useTransform: true (eleventy.config.js:71-74), so custom elements are processed in all output HTML, not only .webc files. (Proof in the wild: src/posts/articles/2022/2022-10-31-post-with-video.md uses <custom-youtube> directly in a markdown body; attributes are documented in src/posts/docs/video.md.)

{# planned — video.njk #}
{% if video.provider == "file" %}
  <video class="u-video" controls preload="metadata"
         poster="{{ video.poster }}" src="{{ video.src }}"></video>

{% elif video.provider == "youtube" %}
  <custom-youtube @slug="{{ video.slug }}" @label="{{ title }}"
    {% if video.poster %}@poster="{{ video.poster }}"{% endif %}></custom-youtube>

{% elif video.provider == "peertube" %}
  <custom-peertube @instance="{{ video.instance }}"
    @embed-slug="{{ video.embedSlug }}" @slug="{{ video.slug }}"
    @label="{{ title }}"></custom-peertube>
{% endif %}
ProviderRendersComponent / elementPoster
fileNative player<video class="u-video">video.poster via poster attribute
youtubeLite YouTube embed<custom-youtube> (lite-youtube + <is-land on:visible>)@poster if set; else auto-derived from v1.opengraph.11ty.dev (custom-youtube.webc:4-7)
peertubeSandboxed iframe embed<custom-peertube> (<is-land on:visible> + sandboxed <iframe>)no auto-poster; supply video.poster if a thumbnail is wanted on the page/card

Both embed components degrade gracefully. Each wraps its player in <is-land on:visible> (lazy-hydrated) and emits a plain <custom-youtube-link> / <custom-peertube-link> anchor as the no-JS fallback (custom-youtube.webc:59, custom-peertube.webc:50-54). The Video layout inherits this behavior for free; it is not re-implemented here.

Available embed attributes (from the components, not re-specified): custom-youtube — @slug, @start, @label, @poster, @posterSize, @jsapi. custom-peertube — @instance, @embed-slug, @slug, @start, @label. The frontmatter (§4) maps onto these. A video.start field could be added later to expose @start; not in v1. (open)

7. Card

Video will use a bespoke src/_includes/partials/card-video.njk (planned) — not the shared card-response.njk. The card is media-led: a poster thumbnail in the image slot, a play affordance, the title, date, and a duration badge.

SlotContent
imagevideo.poster via the image shortcode → <picture slot="image">; for youtube without a poster, the auto-derived thumbnail. A play-icon overlay marks it as video.
headlinetitle if present, linked to the post (omitted / computed for title-less videos)
datedate via date.njk; "draft" badge when draft: true
contentitem.data.description; a duration badge from video.duration
footercategory ("video")

Planned — not yet built. card-video.njk does not exist. It bundles css/custom-card.css like the other cards. The card links through to the post page (it does not embed a player per card — a wall of lazy iframes/players is heavy). The play-overlay styling is a small CSS detail to settle at build. (open)

8. Archive page config

src/pages/videos.njk (planned) drives the listing through archive-listing.njk, modeled on the watching.njk page — a uniform poster-and-text card list in date order:

pagination: { data: collections.video, size: 10 }
permalink:  videos/[page-N/]index.html
cardPartial = "card-video.njk"
collectionToPaginate = collections.video
paginationMetaKey = "blog"

A masonry grid (as the plan gives Photo) is not specified for Video — posters are uniform 16:9 thumbnails, so a regular card grid reads better. Confirm archive-listing.njk variables at build time.

9. Feed — RSS 2.0 (mirrors Audio, with an enclosure-or-link rule)

Video shares Audio's RSS 2.0 body — src/_includes/feeds/podcast-body.njk (to-build; see the Audio spec §8 for the full structure and namespaces). The whole site's other feeds are Atom + JSON Feed whose shared bodies emit only post.content (atom-body.njk:37-39), so this is a new template, not a clone.

{# planned — src/feeds/videos.xml.njk #}
---
permalink: /videos/feed.xml
eleventyExcludeFromCollections: true
excludeFromSitemap: true
---
{%- set feedCollection = collections.video -%}
{%- set feedTitle = "Videos" -%}
{%- set feedDescription = "..." -%}
{%- set feedSelfUrl = "/videos/feed.xml" -%}
{%- include "feeds/podcast-body.njk" -%}

The enclosure-or-link asymmetry (design increment decision). A self-hosted (file) entry has a real local file → it gets a true <enclosure url length type>, exactly like an audio episode (a "vodcast"). An embed entry (youtube/peertube) has no local file to stat and enclose → it carries no enclosure; the item links to the post page (and to the watch URL), and the post page hosts the embed. So podcast-body.njk emits <enclosure> only when video.provider == "file". The exact per-entry conditional is a build detail flagged here. (to-build)

Reused, not rebuilt: pubDate uses the RSS plugin's dateToRfc822 filter (already registered — eleventy.config.js:68, rssPlugin.js:21); absoluteUrl (same plugin) absolutizes URLs. The one to-build formatter shared with Audio is itunes:duration (ISO-8601 → HH:MM:SS).

10. Enclosure derivation (file provider only)

Identical to Audio's mechanism (see the Audio spec §9) and the same shared filter — it applies to Video only when video.provider == "file". The <enclosure> needs url (absolute URL of the passthrough-copied file), length (fs.stat(...).size), and type (extension → MIME, e.g. .mp4→video/mp4, .webm→video/webm). No such filter exists in src/_config/filters/ (verified) — it is to-build, written once and shared by both media types. Embed entries skip it entirely (no local file).

12. JSON-LD / Schema.org

StageValue
Phase 3b (planned, v1)schema: BlogPosting (set in video.njk front matter) → src/_includes/schemas/BlogPosting.njk
Target (to-build)VideoPosting — a BlogPosting envelope embedding a VideoObject (contentUrl for file, embedUrl for embeds, thumbnailUrl, duration)

Why v1 keeps BlogPosting. The schema include is {%- include "schemas/" + schema + ".njk" -%} (src/_includes/head/schema.njk:4), which throws if the template is missing. Only BlogPosting.njk and WebSite.njk exist (verified) — there is no VideoPosting.njk or VideoObject.njk. Asserting schema: VideoPosting before the template exists would break the build. v1 keeps BlogPosting (consistent with Audio, Photo, and the light types); the VideoObject embed is documented as the target and listed in §16, not wired here. VideoObject is the type Google reads for video rich results, so it is a worthwhile Phase-4 follow-up.

14. Collection registration (wiring)

Video registers through the same POST_TYPES mechanism the light types use (Phase 3a Step 0 refactor):

// src/_config/collections.js
export const POST_TYPES = ['article','note','reading','jam','watching', ... ,'video'];

// eleventy.config.js
POST_TYPES.forEach(t => eleventyConfig.addCollection(t, byCategory(t)));

// Layout alias — added explicitly, NOT looped over POST_TYPES:
eleventyConfig.addLayoutAlias('video', 'video.njk');

Layout aliases stay explicit. Do NOT fold layout aliases into the POST_TYPES.forEach loop — POST_TYPES includes article, which has no article.njk (it uses layout: post), so a generic alias loop would emit a bogus alias.

Category names never enter tags, so "video" does not pollute /tags/.
