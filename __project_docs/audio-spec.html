post-type spec

Audio

Planned · Phase 3b · type and namespace audio · designed from the Phase 3 plan 22 May 2026

An Audio post is a self-hosted audio publication — a podcast episode, a recording, a track the author hosts and wants to syndicate. Its primary content is an audio file the author owns, exposed both as an on-page <audio> player and as a podcast <enclosure> in a real RSS 2.0 feed. Audio is one of the two creator-side, hosted-media types (with Video); the two are designed together because they share the enclosure derivation, the RSS 2.0 media feed, and the bespoke media-led card.

Provenance. Audio + Video are the second heavy Phase 3b increment (after Photo), designed together in one pass. The Phase 3 plan only outlines Audio (podcast-shaped RSS 2.0 with <enclosure> byte/MIME derivation + iTunes namespace + transcript; schema AudioPosting embedding AudioObject). The field shapes, transcript handling, feed structure, and the build-vs-defer calls below are decisions of the 22 May 2026 design increment (_generated/Plan - Audio + Video post types (Phase 3b design).md), built on the plan — not invented to fill the page. "The plan specifies …" means the Phase 3 plan; "the design increment decides …" means the 22 May pass. Several mechanisms here do not exist in the codebase yet (the enclosure filter, the RSS 2.0 podcast body, the AudioObject schema); each is marked to-build rather than asserted as wired.

1. Identity

Unlike the shipped types and Photo — which are asymmetric (singular type, plural URL) — Audio is symmetric: "audio" is a mass noun with no natural plural ("audios" reads wrong), so the type, category, folder, URL namespace, archive, and feed all use the same word, audio (design increment decision; confirmed with the author).

Jam precedent for asymmetry; Audio is the symmetric case. Jam is the singular type at a plural URL (/jams/); Photo is photo/photos. Audio simply has no useful plural, so every facet is audio. The collection, layout alias, and category are all audio — there is nothing to "fix" here.

Slug derives from the filename via | slugify. Audio is title-optional (design increment decision — the plan marks only Recipe and Event title-required), following the shipped and light types. In practice a podcast episode almost always has a title, and the feed needs a non-empty <title> per item, so a title-less episode falls back to a computed title (§8).

JSON feed? The shipped feed-bearing types ship an Atom + JSON Feed pair. Audio ships only an RSS 2.0 feed (/audio/feed.xml): podcast clients (Apple Podcasts, Overcast, Pocket Casts) consume RSS 2.0 with enclosures, and JSON Feed has no equivalent podcast enclosure convention. A parallel JSON or Atom feed is a possible later add, not specified here. (open)

4. Frontmatter (planned)

The shape below is the planned authoring surface decided by the 22 May design increment. No sample file exists yet. category, layout, and permalink are not authored per-post — they come from the folder data file src/posts/audio/audio.json (see §1, §12). Audio uses a page bundle (post folder named after the post; media co-located) so the audio file and transcript live next to the .md.

---
audio:
  src: ./episode-12.mp3        # required — co-located audio file (page bundle)
  duration: PT41M12S           # recommended — ISO-8601; surfaces as itunes:duration
  episode: 12                  # optional — itunes:episode
  season: 1                    # optional — itunes:season
transcript: ./episode-12.vtt   # optional — co-located transcript (WebVTT)
poster: ./episode-12-art.jpg   # optional — episode artwork (via image shortcode)
title: "Designing in the open"     # optional (title-optional type — §3)
date: 2026-06-01T09:00:00+02:00    # required — publish timestamp
description: "A short summary for the feed and the card."   # recommended
draft: true                    # optional
tags:
  - podcasting                 # optional — topic tags, NOT the category
---
FieldReq?Role
audiorequiredNested object holding the media (mirrors Photo's photo: object so the two siblings author alike).
audio.srcrequiredBundle-relative path to the source audio file. Drives the on-page <audio> and the feed <enclosure>. Must be a local file — the enclosure length/type are stat-ed from disk (§9).
audio.durationrecommendedISO-8601 duration (e.g. PT41M12S); rendered as itunes:duration in the feed and a duration badge on the card. (An ISO-8601 → HH:MM:SS formatter is to-build — see §8.)
audio.episode / audio.seasonoptionalEpisode/season numbers → itunes:episode / itunes:season.
transcriptoptionalBundle-relative path to a co-located transcript (WebVTT recommended). Surfaced on-page in a <details> and in the feed as <podcast:transcript> (§10-transcript handling, below).
posteroptionalEpisode artwork; rendered via the image shortcode (the Photo poster pattern) for the page and card.
titleoptionalHeadline; falls back to slug, and to a computed feed title when absent (§8). Title-optional type (§3).
daterequiredPublish timestamp (sort + dt-published + RSS pubDate).
descriptionrecommendedCard excerpt and feed <description>.
draftoptionalWhen true, the card shows a "draft" badge; the post is still built in dev.
tagsoptionalTopic tags. Not the category.

Co-located media needs passthrough wiring — a real build detail. Eleventy Image (the image shortcode) handles images; it does nothing for .mp3/.m4a/.vtt. For the on-page <audio src> and the feed enclosure URL to resolve, the co-located audio + transcript must be passthrough-copied to dist/ (an addPassthroughCopy rule for the audio/transcript extensions, or per-bundle copy). This is not wired today and is flagged as a build prerequisite, not asserted as solved. (to-build)

h-entry nesting caveat — DEFERRED. Modeling on watching.njk puts the visible u-audio and .e-content outside the only h-entry in the layout (the hidden authorship block), so a strict mf2 parser won't tie the audio to the entry. Accepted for v1 because webmention sending isn't wired yet. Fix in the webmention milestone — either give the audio layout a self-contained h-entry, or restructure the shared chrome (which also fixes the existing types). Same caveat as the shipped, light, and Photo types.

Audio will use a bespoke src/_includes/partials/card-audio.njk (planned) — not the shared card-response.njk. The card is media-led: episode artwork in the image slot, with the title, date, a duration badge, and the description below.

Planned — not yet built. card-audio.njk does not exist. It bundles css/custom-card.css like the other cards. Whether the card embeds a mini <audio> player or only links through to the post page is an open detail — a player per archive card is heavier and is not the v1 default. (open)

7. Archive page config

src/pages/audio.njk (planned) drives the listing through the shared archive-listing.njk partial, modeled on the watching.njk page. Unlike Photo (which the plan wraps in a <custom-masonry> grid), Audio is a uniform episode list — artwork-and-text cards in date order, newest first:

pagination: { data: collections.audio, size: 10 }
permalink:  audio/[page-N/]index.html
cardPartial = "card-audio.njk"
collectionToPaginate = collections.audio
paginationMetaKey = "blog"

No masonry: episodes are a chronological feed, not an image wall. The exact archive-listing.njk variables match the shipped watching.njk page; confirm at build time.

8. Feed — RSS 2.0 podcast

This is the section that makes Audio a heavy type. The whole site's feed layer is Atom + JSON Feed — every src/feeds/*.xml.njk includes feeds/atom-body.njk (verified: jams.xml.njk), and both shared bodies emit only post.content via renderTransforms, no frontmatter fields (src/_includes/feeds/atom-body.njk:37-39, src/_includes/feeds/json-body.njk:27). A podcast feed is a fundamentally different template — RSS 2.0, not Atom — so it is built fresh, not cloned (design increment decision; confirmed with the author):

{# planned — src/feeds/audio.xml.njk #}
---
permalink: /audio/feed.xml
eleventyExcludeFromCollections: true
excludeFromSitemap: true
---
{%- set feedCollection = collections.audio -%}
{%- set feedTitle = "Audio" -%}
{%- set feedDescription = "..." -%}
{%- set feedSelfUrl = "/audio/feed.xml" -%}
{%- include "feeds/podcast-body.njk" -%}   {# NEW shared body — to-build #}

The new src/_includes/feeds/podcast-body.njk emits RSS 2.0 with the iTunes + Podcast namespaces:

<rss version="2.0"
     xmlns:itunes="http://www.itunes.com/dtds/podcast-1.0.dtd"
     xmlns:podcast="https://podcastindex.org/namespace/1.0">
  <channel>
    <title>{{ feedTitle }}</title>
    <link>{{ meta.url }}/audio/</link>
    <description>{{ feedDescription }}</description>
    <language>{{ meta.lang }}</language>
    <itunes:author>{{ meta.author.name }}</itunes:author>
    <itunes:image href="{{ channelArtwork }}"/>   {# REQUIRED by Apple #}
    <itunes:category text="..."/>
    <itunes:explicit>false</itunes:explicit>
    <itunes:owner>
      <itunes:name>{{ meta.author.name }}</itunes:name>
      <itunes:email>...</itunes:email>
    </itunes:owner>
    {%- for post in feedCollection | reverse -%}
    <item>
      <title>{{ post.data.title or computedTitle }}</title>
      <description>{{ post.data.description }}</description>
      <enclosure url="{{ enclosureUrl }}" length="{{ bytes }}" type="{{ mime }}"/>
      <guid isPermaLink="true">{{ absolutePostUrl }}</guid>
      <pubDate>{{ post.date | dateToRfc822 }}</pubDate>   {# RFC-822 (RSS), not RFC-3339 (Atom) #}
      <itunes:duration>{{ post.data.audio.duration | itunesDuration }}</itunes:duration>
      {%- if post.data.audio.episode %}<itunes:episode>{{ post.data.audio.episode }}</itunes:episode>{% endif -%}
      {%- if post.data.transcript %}<podcast:transcript url="{{ transcriptUrl }}" type="text/vtt"/>{% endif -%}
    </item>
    {%- endfor -%}
  </channel>
</rss>

Date format — already covered; duration formatter — to-build. RSS 2.0 dates are RFC-822 (e.g. Mon, 01 Jun 2026 09:00:00 +0200), not the RFC-3339 that Atom uses. The registered @11ty/eleventy-plugin-rss (eleventy.config.js:68) already provides a dateToRfc822 Nunjucks filter (rssPlugin.js:21), so pubDate is not new work — the body just uses dateToRfc822 where the Atom body uses dateToRfc3339. The same plugin also ships absoluteUrl (used for the enclosure URL) and getNewestCollectionItemDate. The one formatter that is to-build is itunes:duration: it wants HH:MM:SS (or whole seconds), so an ISO-8601 → HH:MM:SS filter must be added.

Channel artwork is required. Apple rejects a podcast feed without channel-level itunes:image. Where that artwork URL lives — site meta, a dedicated podcast data file, or a fixed asset — is a build detail to settle when wiring the feed. (open)

Title-less episodes. RSS items need a non-empty <title>; a title-optional episode gets a computed fallback (e.g. "Episode {{ audio.episode }}" or a date-based title). Exact rule deferred. (open)

9. Enclosure derivation (the to-build filter)

The <enclosure> element needs three things: a url (the public, absolute URL of the audio file), a length (the file size in bytes), and a type (the MIME type). The plan calls for stat-ing the file at build. No such filter exists — src/_config/filters/ holds only category, dates, dtcg, markdown-format, slugify, sort-alphabetic, sort-random, splitlines, striptags (verified). So this is real, small build work:

// planned — src/_config/filters/enclosure.js
import { statSync } from "node:fs";
// resolve the bundle-relative audio.src to its source path on disk,
// stat it for byte length, and map the extension to a MIME type.
export const enclosureBytes = (srcPath) => statSync(resolve(srcPath)).size;
export const enclosureType  = (srcPath) => mimeFromExtension(srcPath); // .mp3→audio/mpeg, .m4a→audio/mp4, ...
PieceSourceState
urlAbsolute URL of the passthrough-copied file (§4 note)depends on passthrough wiring — to-build
lengthfs.stat(...).size on the source filefilter — to-build
typeExtension → MIME (small lookup, or a mime dependency)filter — to-build

Resolving the source path is the fiddly part. The filter receives a bundle-relative ./episode.mp3; it must resolve that to an on-disk path (relative to the post's input file) to stat it, while the url attribute needs the output URL. The exact resolution (using page.inputPath, or a precomputed absolute path in the data cascade) is a build detail flagged here, not a finished solution. (to-build)

10. JSON-LD / Schema.org

StageValue

Why v1 keeps BlogPosting. The schema include is {%- include "schemas/" + schema + ".njk" -%} (src/_includes/head/schema.njk:4), which throws if the template is missing. Only BlogPosting.njk and WebSite.njk exist (verified) — there is no AudioPosting.njk or AudioObject.njk. So asserting schema: AudioPosting before the template is created would break the build. v1 keeps BlogPosting (consistent with Photo and the light types); the AudioObject embed is documented as the target and listed in §14, not wired here. This matches the plan's own Phase 3a note ("the include glue throws on a missing template").

Transcript handling

The transcript (design increment decision, confirmed with the author) lives as a co-located bundle file referenced by transcript: frontmatter (§4), and surfaces in three places:

SurfaceHow
On the post pageInside a native <details><summary>Transcript</summary>…</details> disclosure (EE favours native <details> over JS accordions). Renders the transcript text, or links the .vtt.
In the feed<podcast:transcript url="…" type="text/vtt"/> — the Podcast Namespace tag podcast apps read (§8).
Machine-readableThe same .vtt URL serves both the page and the feed; passthrough-copied like the audio file (§4 note).

Open: whether the transcript is rendered inline in the <details> (parsing WebVTT to readable HTML at build) or simply linked for download. v1 can link-only; inline rendering is a nicer follow-up. The on-page surfacing always uses native <details>; <custom-details> is reserved for the docs collection. (open)

12. Collection registration (wiring)

Audio registers through the same POST_TYPES mechanism the light types use (introduced by the Phase 3a Step 0 refactor):

// src/_config/collections.js
export const POST_TYPES = ['article','note','reading','jam','watching', ... ,'audio'];

// eleventy.config.js
POST_TYPES.forEach(t => eleventyConfig.addCollection(t, byCategory(t)));

// Layout alias — added explicitly, NOT looped over POST_TYPES:
eleventyConfig.addLayoutAlias('audio', 'audio.njk');

Layout aliases stay explicit. Do NOT fold layout aliases into the POST_TYPES.forEach loop — POST_TYPES includes article, which has no article.njk (it uses layout: post), so a generic alias loop would emit a bogus alias. Each new type's alias is added explicitly.

Category names never enter tags, so "audio" does not pollute /tags/.

15. Status & open items

Planned — not built; design detailed in the 22 May 2026 increment (Audio + Video designed together). See _generated/Plan - Phase 3 (10 new post types) - final.md §Phase 3b and _generated/Plan - Audio + Video post types (Phase 3b design).md.

  • Phase 3b — no files for this type exist yet. The POST_TYPES refactor (Phase 3a Step 0) is a prerequisite for the wiring in §12.
  • Media model — DECIDED: self-hosted only. A podcast <enclosure> needs a real local file to stat; embedded audio (Spotify/SoundCloud) can't produce one. Field shape audio: { src, duration, episode, season }. See §4.
  • RSS 2.0 podcast feed — DECIDED, body to-build. A fresh feeds/podcast-body.njk (RSS 2.0 + iTunes + Podcast namespaces), not a clone of the Atom/JSON bodies. See §8.
  • Enclosure filter — to-build. fs.stat byte length + extension→MIME; source-path resolution is the fiddly part. See §9.
  • One feed filter — to-build: itunes:duration (ISO-8601 → HH:MM:SS). RFC-822 pubDate is not new work — the registered RSS plugin already ships dateToRfc822 (and absoluteUrl, getNewestCollectionItemDate). See §8.
  • Passthrough copy for media — to-build prerequisite. Eleventy Image doesn't move .mp3/.vtt; the co-located media must be passthrough-copied for the player + enclosure URLs to resolve. See §4.
  • Transcript — DECIDED: co-located file + <details> + <podcast:transcript>. Inline rendering vs link-only is open. See §10 (Transcript handling).
  • Channel artwork source — OPEN. itunes:image is required; where its URL lives is a build detail. See §8.
  • Title-less episode fallback — OPEN. Computed feed title for title-optional episodes. See §3, §8.
  • Schema — BlogPosting v1; AudioPosting/AudioObject to-build. The include throws on a missing template. See §10.
  • Bespoke card — card-audio.njk. Mini-player vs link-through is open. See §6.
  • µf2 h-entry nesting — DEFERRED + documented (v1). Same caveat as every type; fix in the webmention milestone. See §5, §14.
