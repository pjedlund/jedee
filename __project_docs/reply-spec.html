post-type spec

Reply

Planned · Phase 3a · singular reply / plural replies · derived from the Phase 3 plan 22 May 2026

A Reply is a short post responding directly to another URL — a comment, reaction, or pushback aimed at a specific piece of content on the web. The IndieWeb "reply" / in-reply-to post type. The target URL is the primary content; body text is optional.

1. Singular / plural identity

Reply is asymmetric: the type is singular, the URL namespace is plural — and the plural is irregular. "Reply" pluralizes as replies, not replys. Every URL, folder, archive page, feed filename, and nav entry uses replies. Never auto-append s to derive the plural for this type.

2. Naming & aliases

JEDEE's response type is named Reply (singular) / Replies (plural), directly mapping to IndieWeb's "reply" / in-reply-to vocabulary. A Reply post states: "I am responding to this URL." The target URL is mandatory; a prose response in the post body is optional.

TermStatusWhere it appears / why
reply / replieschosen nameType, layout, collection, URL, archive, feed, nav (see §1). Plural is irregular — replies, never replys.
in-reply-toIndieWeb verb — in µf2 classThere is no "reply" microformat property by that exact name; the property is u-in-reply-to. The JEDEE frontmatter key is camelCase inReplyTo (see §4); the IndieWeb semantics live in the µf2 class on the visible anchor (see §5).

camelCase field name (LOCKED): the URL field is inReplyTo, not in-reply-to. Nunjucks interprets hyphenated top-level keys as subtraction. This is a locked decision across all Phase 3a types; the IndieWeb semantics live in the µf2 class, not in the field name.

Reply is title-optional (plan Decision 9). The slug derives from the filename via | slugify, not from a title field. For a title-less reply the filename becomes the slug; e.g. 2026-05-22-example.md → /replies/2026-05-22-example/.

The permalink is authored in the folder data file replies.json, not per-post. Individual posts do not set their own permalink.

4. Frontmatter (planned)

The shape below is the planned authoring surface — no sample post exists yet. Frame everything as the intended design, derived from the Phase 3 plan's per-type specifics table and the locked Decision on camelCase URL fields.

category, layout, and permalink are not authored per-post — they will come from the folder data file src/posts/replies/replies.json (see §1 and §12). The folder data file will also set tags: "posts" (the system tag) so replies appear in the global posts collection; this is separate from per-post topic tags.

5. Microformats (µf2)

The layout src/_layouts/reply.njk WILL emit a visible verb + anchor with the µf2 class on the <a> element. Unlike Jam, which uses a hidden <data> element (because Jams have body content), Reply uses a visible anchor because the target URL often is the post's primary content — a body-less reply is entirely valid. The plan specifies the following layout body:

<p>In reply to <a class="u-in-reply-to" href="{{ inReplyTo }}">{{ inReplyTo }}</a></p>
<div class="e-content">{{ content | safe }}</div>
PropertyClassFrom
Reply targetu-in-reply-toinReplyTo (camelCase frontmatter field)
Bodye-contentpost content (may be empty)
Publisheddt-publisheddate (via entry-header.njk → date.njk)
Authorshiph-entry / h-card / u-authorhidden authorship block, meta.author

h-entry nesting caveat (DEFERRED — v1): cloning note.njk places the visible u-in-reply-to anchor and .e-content outside the only h-entry in the layout (which is the hidden authorship div). A strict mf2 parser will not tie the reply target to the h-entry. This is accepted for v1 because webmention sending is not wired up yet — the target site won't receive a notification regardless. The fix lands at the webmention milestone: either give the response layouts a proper self-contained h-entry, or restructure note.njk and the shared chrome (the latter also fixes all existing types).

Visible anchor, not hidden <data>: the plan is explicit — light response types use a µf2 class on a visible <a>, because the target URL is often the entire content. Contrast Jam, which uses <data hidden class="u-listen-of"> because a Jam always has a body.

6. Card

Reply will use the shared card-response.njk partial (planned), one card for all five Phase 3a light types. It is modeled on card-notes.njk but drops the title-and-headline assumption, because response posts are often title-less. The plan specifies:

  • A <custom-card> WebC component (no img-square, no image slot).
  • Date, a verb-prefixed target link (verb derived from item.data.category), and a description excerpt if present.
  • Includes css/custom-card.css.
SlotContent
datedate via date.njk; prepended with a "draft" badge when draft: true
target linkverb-prefixed anchor to inReplyTo (e.g. "In reply to <URL>")
contentdescription excerpt, if present

The card-response.njk partial is planned but not built. It will live at src/_includes/partials/card-response.njk and will be created in Phase 3a Step 1, before any individual type is wired up.

8. Feed

Reply has a feed — YES. A pair of feed templates will be created (plan Step 5 for Bookmark/Reply/RSVP), cloned from src/feeds/notes.json.njk and notes.xml.njk:

# replies.xml.njk
permalink: /replies/feed.xml
feedCollection = collections.reply
feedTitle = "Replies"
feedDescription = "Replies to posts around the web."
feedSelfUrl = "/replies/feed.xml"
→ includes feeds/atom-body.njk

# replies.json.njk — same vars, with:
permalink: /replies/feed.json
feedSelfUrl = "/replies/feed.json"
→ includes feeds/json-body.njk

The permalink: frontmatter (not the filename) controls the output path. The plan explicitly warns: leaving the cloned permalink: /notes/feed.xml collides with the Notes feed and errors the build (duplicate permalink). Update the permalink when cloning.

Title-less entry wrinkle

Reply is title-optional. A title-less entry produces an empty <title></title> element in the Atom feed. The plan flags this as an open question:

  • Option A (open): compute a fallback title — e.g. "Reply to <host>" — from the inReplyTo URL's hostname, so feed readers show something meaningful.
  • Option B: accept the empty <title> for v1; address it when feed rendering is revisited.

The plan records this as still open. See §14 (Status & open items) for the tracking note. Until resolved, v1 ships with whatever the cloned feed template produces (likely an empty title for title-less entries).

9. Navigation

Reply will be listed in the Posts submenu in src/_data/navigation.js (planned). The plan specifies:

{ text: 'Replies', url: '/replies/' }

Bookmark, Reply, and RSVP are the three Phase 3a types that get a nav entry. Like and Repost are excluded to avoid nav bloat for the pure-firehose, feedless types.

12. Collection registration (wiring)

Phase 3a begins with a Step 0 refactor that collapses all per-type collection registrations into a POST_TYPES array loop. The plan specifies the following mechanism:

// src/_config/collections.js (after Step 0 refactor)
export const POST_TYPES = [
  'article', 'note', 'reading', 'jam', 'watching',
  'bookmark', 'reply', 'rsvp', 'like', 'repost'   // reply added in Step 2
];
export const byCategory = cat => collection =>
  collection.getFilteredByGlob('./src/posts/**/*.md')
    .filter(item => item.data.category === cat)
    .reverse();

// eleventy.config.js (after Step 0 refactor)
import { POST_TYPES, byCategory, showInSitemap, tagList } from './src/_config/collections.js';
POST_TYPES.forEach(t => eleventyConfig.addCollection(t, byCategory(t)));

// Layout alias — added EXPLICITLY, not looped:
eleventyConfig.addLayoutAlias('reply', 'reply.njk');

Why the layout alias is explicit, not looped: POST_TYPES includes article, which has no article.njk (it uses layout: post — see articles.json). A generic POST_TYPES.forEach(t => addLayoutAlias(t, t + '.njk')) loop would emit a bogus addLayoutAlias('article','article.njk'). Every type gets its alias added individually alongside the existing shipped aliases.

The folder data file's extensionless layout: "reply" requires the alias to resolve. Without the alias, Eleventy cannot find reply.njk.

Category names never enter tags, so reply does not pollute /tags/.

13. Webmentions

Webmention is the IndieWeb's federated response protocol — a Reply post is exactly the kind of post that should send a webmention to the target URL. Nothing here is reply-specific; the plumbing is shared by every post type and Reply will inherit it through the base layout and entry-footer.njk. Discovery is shipped; receiving and sending are deferred to the webmention milestone.

PieceStateWhere
Endpoint discoveryshipped (Phase 1)<link rel="webmention" href="https://webmention.io/johanedlund.se/webmention"> in <head> via src/_includes/head/meta-info.njk (reply will use layout: base).
Authorship h-cardshippedThe hidden h-entry authorship block in the cloned layout will carry u-url, p-name u-url rel="author", and a u-author h-card avatar so a receiver can attribute the post (§5).
Render slotwired, no-op (once built)reply.njk → entry-footer.njk → partials/webmentions.njk, currently an empty stub — safe to call while the renderer is empty.
Receiving / renderingdeferredThe webmention milestone wires a webmention.io fetch (via @11ty/eleventy-fetch, ~24 h cache); webmentions.njk then groups received mentions by type (likes / replies / reposts / mentions).
SendingdeferredOutgoing webmentions aren't wired. A Reply post will not notify the target URL until the sending side of the webmention milestone lands — even though sending is semantically the primary use case for a Reply. This is intentional for v1.

h-entry nesting (§5). The only h-entry in the planned layout is the hidden authorship block; the visible u-in-reply-to anchor and .e-content will sit outside it, so a strict mf2 parser won't tie the reply target to the entry. Harmless while sending is deferred; fix it when the webmention sending milestone lands — see §5 and §14.
