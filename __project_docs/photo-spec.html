post-type spec

Photo

Planned · Phase 3b · singular photo / plural photos · designed from the Phase 3 plan 22 May 2026

A Photo is a post whose primary content is an image — a single photograph the author wants to publish, optionally with a caption and a short note. The IndieWeb "photo" post type. Unlike the Phase 3a light types (Bookmark, Like, …) whose content is an outbound link, a Photo's content is the image itself, so the type carries a real u-photo and a bespoke image-led card.

Provenance. Photo is the first of the five heavy Phase 3b types to get a design pass. The Phase 3 plan only outlines it (u-photo + alt; single-photo default + opt-in gallery; masonry archive; new card-photo.njk). The field shapes, feed handling, and schema choices below are decisions of the 22 May 2026 design increment (_generated/Plan - Photo post type (Phase 3b design).md), built on top of the plan — not invented to fill the page. Where something is still undecided, this spec says so rather than guessing. Throughout, "the plan specifies …" means the Phase 3 plan; "the design increment decides …" means the 22 May pass.

1. Singular / plural identity

Photo is asymmetric, like the shipped and light types: the type is singular, the URL namespace is plural. The Eleventy collection will be named with the singular (collections.photo), but the folder, URL, archive, and feed will all use the plural.

As with Jam and the light types: the folder will be photos/ but its data file will set category: "photo", and the collection registered from that category will be photo (singular). Don't "fix" this — the layout alias, collection, and category are all singular by design.

2. Naming & aliases

JEDEE's image type is named Photo (singular) / Photos (plural), following the IndieWeb's established "photo" post type. The type name and the microformat property share the same word.

u-photoIndieWeb µf2 propertyThe microformat for an image embedded in an h-entry. Emitted as a class on the rendered <img> (§5), not a frontmatter key.
galleryrelated, deferredEE already ships a gallery: frontmatter convention + gallery.njk partial for multi-image posts. The single-photo default is the Photo type's v1; the gallery is a documented future opt-in (§13), not a separate type.

Slug derives from the filename via | slugify. Photo is a title-optional type: a post without a title is valid — the image is the primary content. The plan marks only Recipe and Event as title-required; Photo follows the title-optional pattern of the shipped and light types (design increment decision).

4. Frontmatter (planned)

The shape below is the planned authoring surface decided by the 22 May design increment. No sample file exists yet. category, layout, and permalink are not authored per-post — they will come from the folder data file src/posts/photos/photos.json (see §1 and §12).

---
photo:
  src: ./src/assets/images/photos/sunset-over-the-fjord.jpg  # required
  alt: A low orange sun setting behind a still fjord         # required (convention — see note)
  caption: Sognefjord, an hour before midnight               # optional
title: Sunset over the fjord       # optional
date: 2026-06-01T21:30:00+02:00    # required — post timestamp
description: A short note about the shot.   # recommended
draft: true                        # optional
tags:
  - photography                    # optional — topic tags, NOT the category
---
FieldReq?Role
photorequiredNested object holding the image. The design increment chose a nested object (over flat top-level keys) so the image's data stays grouped and maps 1:1 to the image shortcode's positional (src, alt, caption) arguments.
photo.srcrequiredPath to the source image. The image shortcode prepends ./src if absent (src/_config/shortcodes/image.js:37), and throws if src is missing (image.js:93).
photo.altrequired (convention)Alt text → carried onto the <img> and used for u-photo accessibility. See the note below.
photo.captionoptionalWhen present, the image shortcode wraps the picture in a <figure> with a <figcaption> (image.js:76-78).
titleoptionalHeadline; falls back to slug. Title-optional type (§3).
daterequiredPost timestamp (sort + dt-published).
descriptionrecommendedCard excerpt and feed summary; a short note about the photo.
draftoptionalWhen true, the card shows a "draft" badge; post is still built.
tagsoptionalTopic tags. Not the category.

Alt is required by convention, not by EE. Eleventy Excellent's image shortcode does not enforce alt — it defaults alt = '' (image.js:21) and only throws on a missing src (image.js:93). The Photo type requires alt as its own authoring rule: the photo is the content, so a photo post without alt text is incomplete and fails accessibility. This is a design-increment decision; the build will not stop you, so the requirement lives in the spec and in review, not in tooling (a lint could enforce it later).

Asset path. The illustrative ./src/assets/images/photos/<file> path mirrors EE's existing /assets/images/gallery/ and JEDEE's /assets/images/listening/ conventions. Co-locating the image in a per-post page bundle is a likely future direction for Photo, but is not settled here. (Note this is the co-located body-image case, distinct from the fetched-cover pattern the rich-media types use — see build-time cover images §4. A remote u-photo would instead take the plain-<img> path.) (open)

5. Microformats (µf2)

The layout will be src/_layouts/photo.njk (planned), modeled on the existing per-post layouts (e.g. watching.njk). Unlike the light types — whose target is a visible outbound <a> — a Photo's content is the image, so u-photo goes on a visible <img> rendered above the body:

{# planned — renders the photo with u-photo via the image shortcode's imageClass param #}
{% image photo.src, photo.alt, photo.caption, "eager", "", "u-photo" %}

<div class="e-content">{{ content | safe }}</div>
PropertyClassFrom
Photou-photo (on the <img>)photo.src + photo.alt
Bodye-contentpost content (may be empty)
Publisheddt-publisheddate (via entry-header → date.njk)
Authorshiph-entry / h-card / u-authorhidden block, meta.author

How u-photo lands on the <img>. EE's image shortcode accepts an imageClass parameter (6th positional arg, or imageClass via the named imageKeys shortcode) that it writes onto the <img> (image.js:70). Passing "u-photo" there is the planned mechanism — it works whether the shortcode emits a bare <picture> or wraps it in a <figure> for a captioned photo, because the class is on the inner <img> either way.

Stray slot="image" — minor wrinkle. The image shortcode hardcodes slot="image" on its <picture>/<figure> (image.js:74,77-78) because it was written to feed <custom-card> (§6). Used in the post layout (outside a custom element) that attribute is inert — harmless, just semantically idle. If it grates, a slot-less image variant is the alternative. (open — accept the inert attribute, or add a slot-less variant.)

h-entry nesting caveat — DEFERRED. Modeling on watching.njk puts the visible u-photo and .e-content outside the only h-entry in the layout (the hidden authorship block), so a strict mf2 parser won't tie the photo to the entry. Accepted for v1 because webmention sending isn't wired up yet. Fix in the webmention milestone — either give the photo layout a self-contained h-entry, or restructure the shared chrome (which also fixes the existing types). Same caveat as the shipped and light types.

6. Card

Photo will use a bespoke src/_includes/partials/card-photo.njk (planned) — not the shared card-response.njk of the light types, which has no image slot. The card is image-led: the photo fills the card's image slot, with minimal text below.

This is exactly what EE's image shortcode is built for: it emits <picture slot="image"> (or <figure slot="image"> when captioned), which slots directly into the <custom-card> WebC component's image slot.

SlotContent
imagephoto.src + photo.alt via the image shortcode → <picture slot="image">
headlinetitle if present, linked to the post (omitted for title-less photos)
datedate via date.njk; prepended with a "draft" badge when draft: true
contentitem.data.description if present
footercategory ("photo")

Planned — not yet built. card-photo.njk does not exist yet. It bundles css/custom-card.css like the other cards. Whether the card carries u-photo on its image (so archive thumbnails are themselves valid µf2) or leaves u-photo to the post page only is an open detail. (open)

7. Archive page config

src/pages/photos.njk (planned) will drive the listing through the shared archive-listing.njk partial, modeled on the watching.njk page. The plan specifies the archive wraps its cards in a <custom-masonry> grid — an image-led masonry layout rather than the uniform card rows of the text types:

pagination: { data: collections.photo, size: 10 }
permalink:  photos/[page-N/]index.html
cardPartial = "card-photo.njk"
masonryLayout = "50-50"
collectionToPaginate = collections.photo
paginationMetaKey = "blog"

custom-masonry is shipped. The <custom-masonry> web component (src/assets/scripts/components/custom-masonry.js) already exists — it positions grid children by computed column count on load and resize. The Photo archive consumes it; it is not new work. How archive-listing.njk wraps cards in <custom-masonry> for the image grid (vs. the existing masonryLayout handling) is the one archive detail to confirm at build time. (open)

8. Feed

Photo gets a feed (design increment decision): photo posts are followable content — a photoblog. A pair of templates will be cloned from src/feeds/notes.json.njk and notes.xml.njk to src/feeds/photos.json.njk and photos.xml.njk, setting the permalink: frontmatter (this, not the filename, controls the output path) and the feed variables:

# photos.xml.njk
permalink: /photos/feed.xml
feedCollection = collections.photo
feedTitle = "Photos"
feedDescription = "Photographs I've published."
feedSelfUrl = "/photos/feed.xml"
→ includes a photo-aware body (see wrinkle)

# photos.json.njk — same vars, with:
permalink: /photos/feed.json
feedSelfUrl = "/photos/feed.json"

The feed wrinkle — a real implementation detail, not a copy-paste. The shared feed bodies emit only post.content — the rendered markdown body via renderTransforms — and render no frontmatter fields (src/_includes/feeds/atom-body.njk:37-39, src/_includes/feeds/json-body.njk:27). Because a Photo's image lives in photo: frontmatter (not the body), a naive clone of the Notes feed would emit Photo entries with the image missing. The Photo feed therefore needs a photo-aware body that renders the photo as an absolute-URL <img> (with alt) ahead of post.content.

Recommended approach (mechanism deferred to build). Add a small photo-specific feed body rather than editing the shared atom-body.njk/json-body.njk that five shipped feeds depend on. The exact wiring — a new partial vs. a parameter on the shared body, and how the relative image URL is absolutized for the feed — is a Phase-3b implementation detail flagged here, not a finished solution. (open)

12. Collection registration (wiring)

Photo registers through the same POST_TYPES mechanism the light types use (introduced by the Phase 3a Step 0 refactor):

// src/_config/collections.js
export const POST_TYPES = ['article','note','reading','jam','watching', ... ,'photo'];

// eleventy.config.js
POST_TYPES.forEach(t => eleventyConfig.addCollection(t, byCategory(t)));

// Layout alias — added explicitly, NOT looped over POST_TYPES:
eleventyConfig.addLayoutAlias('photo', 'photo.njk');

Layout aliases stay explicit. As the plan stresses, do NOT fold layout aliases into the POST_TYPES.forEach loop — POST_TYPES includes article, which has no article.njk (it uses layout: post), so a generic alias loop would emit a bogus alias. Each new type's alias is added explicitly.

Category names never enter tags, so "photo" does not pollute /tags/.

13. Gallery (multi-image) — deferred opt-in

The Phase 3 plan pairs the single-photo default with an "opt-in gallery." The 22 May design increment scoped v1 to single-photo only and defers the gallery so the spec doesn't invent a multi-image field shape. The gallery is a documented future opt-in, not a separate post type.

EE already ships the machinery: a gallery: [{ image, alt, caption }, …] frontmatter array and src/_includes/partials/gallery.njk, which renders a thumbnail grid of <button>s inside an <is-land on:idle>, each opening an image in a <dialog> lightbox (styled by gallery.css, behaviour in dialog.js). A multi-image Photo would set gallery: and the layout would include gallery.njk.

Open gaps for the gallery opt-in (not designed yet):

  • µf2 on gallery images. The current gallery.njk calls {% image item.image, item.alt %} with no imageClass, so gallery images do not carry u-photo. A Photo-gallery variant would need to pass imageClass: "u-photo" per image (each photo a u-photo in the h-entry). Deferred.
  • Field reconciliation. Whether the single-photo photo: object and the gallery's gallery: array coexist as two fields, or are later unified, is not decided. v1 ships photo: only; the gallery reuses EE's existing gallery: shape verbatim if/when adopted.
  • Card & feed for galleries. How a multi-image post renders in card-photo.njk (first image? collage?) and in the feed is unspecified.

14. Webmentions

Webmention is the IndieWeb's federated response protocol. Nothing here is Photo-specific — the plumbing is shared by every post type and Photo will inherit it through the base layout and entry-footer.njk. Discovery is shipped; receiving and sending are deferred to the webmention milestone.

PieceStateWhere
Endpoint discoveryshipped (Phase 1)<link rel="webmention" …> in <head> via src/_includes/head/meta-info.njk (photo will use layout: base).
Authorship h-cardplannedThe hidden h-entry block carried into photo.njk will provide u-url, p-name u-url rel="author", and a u-author h-card avatar so a receiver can attribute the post (§5).
Render slotplanned, will be no-opphoto.njk → entry-footer.njk → partials/webmentions.njk, currently an empty stub — safe to call while the renderer is empty.
Receiving / renderingdeferredThe webmention milestone wires a webmention.io fetch (via @11ty/eleventy-fetch, ~24 h cache); webmentions.njk then groups received mentions by type.
SendingdeferredOutgoing webmentions aren't wired.

h-entry nesting (§5). The only h-entry in the layout will be the hidden authorship block; the visible u-photo and .e-content will sit outside it. Harmless while sending is off; fix it when the sending side of the webmention milestone lands.
