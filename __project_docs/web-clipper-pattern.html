cross-cutting convention

Web Clipper templates

Drafted 24 May 2026, updated 25 May (property-type registry) · 3 templates live (reading, watching, notes) · ~9 in the v1 plan · the ingestion layer for every browser-authored post type

Most JEDEE posts about someone else's thing — a book, a film, an album, a bookmarked page — are authored not by hand but by clipping: right-click a source page in the browser, pick a template, and a shape-correct .md lands in the right src/posts/<type>/ folder. The tool is the Obsidian Web Clipper (a browser extension), and each post type that can be clipped has one or more per-source JSON templates. This page is the canonical write-up of that layer: how a template is shaped, the type-discipline rules that keep frontmatter valid, the live-vs-export drift trap, and the per-type inventory of what exists versus what's planned.

Scope. This documents the convention and current state, and tracks the work of building/fixing the templates. It is not the per-template field design — that lives in __design/Step 4 - Clipper layer design.md (the structural source) and must be reconciled against the current canonical spec __design/Plan - Phase 3 (10 new post types) - final.md before any template is authored (see §9). Where this doc and Step 4 disagree, this doc reflects what's true on disk today.

1. The clipper layer — what it is

The Obsidian Web Clipper is JEDEE's primary CMS for browser-shaped post types. A template triggers on a URL (or on a schema.org @type), reads the source page's JSON-LD / meta tags / DOM selectors, and writes a frontmatter-complete .md into a target folder — no per-post hand-editing. Three components collaborate; knowing which owns what makes the rest fall out:

ActorOwnsState
Obsidian Web Clipper (browser extension)Reading the source page and writing a shape-correct .md with cover: <remote-URL> in frontmatterPer-source JSON templates in src/_obsidian/clipper/<source>-clipper.json
obsidian-local-images-plus (vault plugin)Downloading body images (not frontmatter) next to the note, MD5-named, idempotentInstalled; automatic mode, "in folder named after note"
normalize-posts.js (setup script)Cover colocation + bundle promotion + drift renamesDropped, never built — superseded by build-time cover fetch (§6)

Division of labor: local-images-plus only touches body content, never YAML. Covers are data (cards, OG meta, JSON-LD), so they stay in frontmatter and are self-hosted at build (§6) — they are never pushed into the body just to let the plugin handle them.

2. Where templates live — and the drift gotcha

Each template has two copies, and they can silently diverge:

CopyWhereRole
Exported JSONsrc/_obsidian/clipper/<source>-clipper.json (git-tracked)The source of truth. Re-importable, reviewable, and version-controlled — git diff surfaces a changed export.
Live templateInside the browser extension's own storageWhat actually runs at clip time. Editable in the extension UI.

The trap: editing the live template in the extension does not update the exported JSON, and vice-versa. The two drift. A clip then behaves according to the live copy, which may no longer match the repo export you're reading.

Cautionary tale (24 May 2026). A Reading clip of A Confession came in with its description shattered into a YAML list at every comma, and its filename carrying the author (… - Leo Tolstoy). The repo export standard-ebooks-clipper.json was correct on both counts (description = text, noteNameFormat = title-only) — the live extension had drifted. Fix: re-import the export to overwrite the live copy. Rule: after editing any template in the extension, re-export it over the repo copy; after editing the repo copy, re-import it. Treat a mismatch as a bug. The exports are now git-tracked (src/_obsidian/clipper/), so re-exporting after an extension edit makes drift visible in git diff.

Correction (25 May) — re-import is not a cure-all. Re-importing the export fixes drift in the template's content — the value expressions, name, and noteNameFormat — but it does not reset a property's type. Types live in a separate registry that import only seeds, never overrides (§4). When Resurrection was re-clipped after the export had been corrected to description: text, the field still arrived as a List, until the type was changed by hand in the Clipper's Properties tab. So the 24 May "fix: re-import" above is necessary but not sufficient — a stuck type needs §4, not another import.

3. Anatomy of a template

A template is a small JSON object. The shape (from src/_obsidian/clipper/letterboxd-clipper.json):

{
  "schemaVersion": "0.1.0",
  "name": "Letterboxd",            // shown in the extension's template menu
  "behavior": "create",            // create a new note
  "noteContentFormat": "",         // the note BODY (often empty; "{{content}}" to capture page text)
  "properties": [                  // → YAML frontmatter, one object per field
    { "name": "title", "value": "{{schema:@Movie:name}}", "type": "text" },
    …
  ],
  "triggers": ["https://letterboxd.com/film/"],   // URL prefix, regex, or "schema:@Type"
  "noteNameFormat": "{{schema:@Movie:name}}",      // the FILENAME (→ slug + wikilink target, §5)
  "path": "posts/watching/"        // destination folder under src/
}
KeyControls
properties[]The frontmatter. Each has a name, a value (template expression), and a type — and type is load-bearing (§4).
value sources{{schema:…}} (JSON-LD), {{selector:…}} (DOM/CSS), {{meta:…}} (meta tags), {{url}}/{{title}}/{{date}}/{{description}} (page variables). Pipe through filters: |wikilink, |split:", ", |join, |safe_name, |date:"YYYY", |first, |slice:0,5.
triggers[]When the template auto-selects. URL prefix, regex, or a schema.org type (schema:@Event, schema:@Recipe). Empty [] = manual pick from the menu.
noteNameFormatThe filename → the slug and the Obsidian wikilink target (§5).
pathDestination folder. Inherited category/layout/permalink come from that folder's <type>.json, so the template need not emit them.

4. Type discipline — type decides the YAML

Each property's type determines how its value is serialized into YAML. This is the single biggest source of clipper bugs.

typeYAML outputUse for
textA scalar stringtitle, description, a single URL, a single name
multitextA YAML list — and the captured value is split on commas into itemsgenuinely multi-value fields: genre, cast, multiple authors, tags
numberA bare numberyear, page count, score
dateAn ISO datepublication / event dates
checkboxtrue/falsedraft
{ "name": "plot",  "value": "{{description}}",  "type": "text" }       // → plot: A scalar sentence, commas and all.
{ "name": "genre", "value": "{{schema:genre}}", "type": "multitext" }  // → genre:
                                                                       //     - Drama
                                                                       //     - Romance

The two failure modes — both stem from putting a single-value field on multitext:

  • Comma shatter. A description like "A meditation on depression, philosophy, religion, and life." on a multitext field becomes a four-item list, split at every comma. (This is exactly what hit A Confession.)
  • Type mismatch. Even with no commas, a single value on multitext becomes a one-item list. Once the property is registered as text vault-wide, Obsidian flags it: "Type mismatch, expected text."

Obsidian's side of the contract: src/.obsidian/types.json registers each property's type vault-wide. Switching a property to "List" in Obsidian's UI splits its value on commas (and switching back does not rejoin). Pin shared scalar properties there — description is now pinned to text — so a stray toggle can't shatter them. Keep the clipper type and the types.json type in agreement.

4a. Where the type actually lives — three registries, and import only seeds

The hard-won lesson (relived 25 May): a property's type is not really owned by the template. It is owned by a registry, and there are three in the pipeline. The template's type field is only a seed — on import it sets the type for a property name a registry has never seen, and it never overrides a name already registered. So re-importing a template (or re-editing the JSON) cannot change a type that has already stuck; you must change it where it actually lives.

RegistryWhere it livesRoleHow to change it
Template typethe JSON's properties[].typeSeed only. Applies the first time a registry meets a property name.edit the JSON, then re-import
Web Clipper Propertiesextension storage — Settings → Properties tab (the propertyTypes map)The type the Clipper actually writes, keyed by property name across all templates. A fresh install ships empty (propertyTypes: []).the Properties tab, or the type icon left of the field in the template editor
Obsidian vaultsrc/.obsidian/types.jsonThe type Obsidian enforces on the note once it lands; a mismatch fires the "type mismatch / Display as text?" warning.the property's type dropdown in Obsidian, or edit types.json and reload

Why re-importing didn't fix it (25 May). After the export was corrected to description: text, the extension still showed description as a List — because its Properties registry already had description registered as List from an earlier multitext import, and import only seeds unseen names. The cure was: change description → Text in the Clipper's Properties tab, then set types.json to text and reload Obsidian. The same rule bit at two layers; the JSON's type was a red herring both times.

Portability payoff — why description is text, not multitext. Because a fresh Web Clipper ships propertyTypes: [] and a fresh vault has no registered description, a new user who imports a template gets every property seeded from the template's type — clean, no warning. A shared, semantically-scalar field declared text (notably description, which is also a recognized Obsidian Publish property, conventionally a single string) therefore lands clean in any fresh setup. Declaring it multitext only stays clean in vaults that happen to register it as List — it trips the warning for the common case where the user already holds description as text. Rule: shared scalar fields go on text; reserve multitext for genuinely multi-value fields (genre, cast, authors). This reverses a brief 25 May detour that had set description to multitext "to tolerate both shapes" — tolerance only helps in a vault you control, not in someone else's.

5. Naming — title-only, for wikilinks

noteNameFormat sets the filename. Keep it the title alone — do not append the author, year, or director. The reasons:

  • Wikilinks resolve on the title. A file named What Is Art - Leo Tolstoy.md means [[What Is Art]] won't resolve; What Is Art.md does.
  • The slug is the filename. JEDEE permalinks derive from {{ page.fileSlug | slugify }}, so What Is Art.md → /reading/what-is-art/. The author suffix just produced an uglier URL.

Always pass the name through |safe_name — it strips filesystem-illegal characters (:, /, ?) that JSON-LD titles sometimes carry (3:10 to Yuma → 310 to Yuma; What Is Art? → What Is Art). It is OS-safety, not kebab-casing — spaces and title-case are preserved, and Eleventy slugifies for the URL at build.

Exception — Jam. The Bandcamp design uses "{{…name|safe_name}}, by {{…byArtist.name|safe_name}}" deliberately, because album titles collide across artists. That's a considered trade against the wikilink-cleanliness rule, not a violation of it. Every other type stays title-only.

6. Covers — emit a URL, the build self-hosts it

An image-led clip (book cover, film poster, album art) writes a single remote URL into a cover: field, as plain text:

{ "name": "cover", "value": "{{schema:image}}", "type": "text" }

The layout renders it as a plain <img>, and Eleventy's always-on Image HTML Transform fetches, optimizes, and self-hosts it at build. The clipper's job ends at "write the URL." See build-time cover images for the full mechanism.

Dropped apparatus — don't resurrect. An earlier design (Step 4, before its 23 May amendment) had a normalize-posts.js / colocate-cover.js script download covers into per-post page bundles, plus a coverSource: field. That was never built — the build self-hosts remote URLs already, so the script was redundant. If you find a clipper template or spec describing co-located covers or coverSource:, it predates the decision. Clips write flat .md files with a remote cover: URL; bundles are opt-in only when a post has genuine co-located body images.

7. Wikilinks

The |wikilink filter wraps values in [[…]] so they join the Obsidian graph; it works on single values and arrays. Compose it with split/join for delimited source strings:

{ "name": "author", "value": "{{author|split:\", \"|wikilink|join}}", "type": "multitext" }

It's the right tool for author / authors (Reading), cast / genre / director (Watching), and artist / genre (Jam). Layouts render the wikilink as plain text — the graph value lives in the source, it needn't leak to HTML.

9. Known issues & fix queue

  • Standard Ebooks — live drift + stuck description type — RESOLVED (25 May). Re-importing the corrected export fixed the content drift (noteNameFormat back to title-only), but the description type stayed List through every re-import — it was stuck in the Clipper's Properties registry (§4a). Fixed by switching description → Text in the Clipper's Properties tab, setting src/.obsidian/types.json to text, and reloading; Resurrection then re-clipped as a clean scalar with no warning. description is now text end-to-end and portable to fresh installs. (closed)
  • Notes clipper reworked. The stale note-to-_sources test file was replaced by notes-clipper.json ("note about a page" → posts/notes/, 24 May). Import the new template into the extension and delete the old "Note to _sources" entry there. (open: import)
  • Field-name reconciliation — RESOLVED (camelCase key, kebab µf2 class). Step 4's kebab targets (read-of, watch-of, bookmark-of, in-reply-to) conflated two layers; the canonical spec (Plan - Phase 3 (10 new post types) - final.md) separates them and locks the rule. The frontmatter data key is camelCase (bookmarkOf, likeOf, inReplyTo, repostOf, rsvp) — Nunjucks reads bookmark-of as subtraction. The IndieWeb semantics ride on the µf2 class on the rendered <a> (class="u-bookmark-of"), which stays kebab. On disk this already holds: the 3 live templates use only camelCase keys (wordCount, myUrl, scoreLB), and the book/film URL is link/url — never read-of. Step 4's kebab keys were thus never built. When authoring a template: camelCase key + kebab µf2 class on the layout's <a>; for types beyond the Phase 3a five (Jam/Bandcamp, Recipe, the Letterboxd edits) take the key from the live type's existing fields, not from Step 4. (resolved 24 May — v1 authoring unblocked)
  • Reading source diverged from the design. Step 4 proposed Open Library as Reading's v1 source; in reality Standard Ebooks was built and shipped. Treat SE as the live Reading clipper; Open Library / Google Books are alternates.
  • types.json coverage. Only description is pinned so far. As clippers add shared scalar properties, pin them in src/.obsidian/types.json to match the clipper type (§4).

10. Authoring the JSON at scale

v1 is ~9 hand-edited JSON files — manageable, and templates rarely change once written. If escaped-string editing becomes painful, the planned escalation (Step 4 § "Templates as code") is a generator: write typed sources at src/_config/setup/clipper-templates/<name>.ts with shared fragments (the common draft/date lines, the wikilink rule), and a setup script emits the JSON into src/_obsidian/clipper/. Forking the extension itself is explicitly rejected until a concrete distribution need exists.
