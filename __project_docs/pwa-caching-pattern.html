PWA caching

Runtime caching shipped 23 Jun 2026 (0275458) · live · no dependencies · extracted from src/pages/serviceworker.njk

JEDEE is an installable Progressive Web App. A service worker — a small script the browser keeps running in the background — sits between every page request and the network and decides, per request, whether the response comes from the network, from a local cache, or both. Until 23 Jun 2026 the worker did only one thing: serve a static /offline/ page when you lost connection. It now does runtime caching — a page you have visited is stored and served back offline, fully styled — in ~25 lines of hand-written JavaScript, no library.

One file, no dependency. The whole behavior lives in src/pages/serviceworker.njk (a templated page that outputs /serviceworker.js), registered by a six-line inline script at the foot of src/_layouts/base.njk. There is no Workbox, no build step, no npm package — see §4 for why.

1. The five strategies

Service-worker caching is conventionally described as five strategies (the same five Workbox names). JEDEE uses three of them; the diagram marks which.

StrategyBehaviorIn JEDEE
Cache firstServe from cache if present; only hit the network on a miss, then store it.Assets — CSS, JS, fonts, images.
Network firstTry the network; fall back to cache when offline. Keeps content fresh.Pages — every navigation.
Stale-while-revalidateServe the cached copy at once and refresh it from the network in the background for next time.Not used. (The natural next strategy — see §6.)
Network onlyAlways the network, never cached.Pass-through — non-GET and cross-origin requests.
Cache onlyAlways the cache, never the network.Not used as a read path. JEDEE precaches a few files but they still fall back to the network on a miss (cache-first), so nothing is pure cache-only.

2. The request router

The worker's fetch handler is a short decision tree, read top to bottom. The diagram is that exact if/else.

  • Network only (pass-through). The handler returns early for any request that isn't a same-origin GET — POSTs, and cross-origin requests such as the hot-linked webmention avatars (which carry eleventy:ignore). The browser handles them normally; nothing is cached.
  • Network first (pages). Navigations try the network first (using navigation preload where supported), so content is always fresh online. A copy of the response is put in the cache in the background. Offline, the handler returns the cached page if you have visited it, and only falls back to /offline/ for a URL it has never seen.
  • Cache first (assets). Everything else same-origin — CSS, JS, fonts, images — is served from cache when present, otherwise fetched and stored. This is what lets a revisited page render fully styled offline, including the hashed /bundle/<hash>.css that can't be precached by hand (see §3).

3. What's cached, and when

Two fill mechanisms, one cache.

 Precache (on install)Runtime (on first request)
WhenOnce, when the worker installs.As each resource is first requested.
What/, the favicon + app icons, and /offline/.Every visited page and every asset it pulls in.
Why this splitA tiny, stable set so the home shell, the install icons, and the offline fallback exist before the first offline visit.The page CSS is served as hashed/query-busted paths (/assets/css/global.css?…, /bundle/<hash>.css) that can't be hard-coded into a precache list — runtime caching grabs them automatically on first load.

The cache resets itself every deploy. The cache is named cache-<buildTime>, stamped at build time. On activate, the worker deletes every cache whose name isn't the current one, so a new deploy wipes the old cache wholesale. That is why aggressive cache-first storage of un-hashed assets is safe here — there is no long-lived staleness to manage. (skipWaiting + clients.claim make the new worker take over immediately rather than waiting for every tab to close.)

ponytail ceiling. The runtime cache is unbounded within a build — there is no per-entry count or age cap. For a personal site that browses a few hundred pages between deploys this is a non-issue, and each deploy clears it. If it ever grows uncomfortable, add per-type expiry (or adopt Workbox, §4) — the upgrade path, not a present need.

4. Why not Workbox

Google's Workbox is the standard library for this. JEDEE deliberately does not use it. The whole need here is ~25 lines of vanilla JavaScript, and the one thing Workbox does that is genuinely awkward by hand — precaching the hashed /bundle/<hash>.css paths with auto-generated revisions — simply disappears once runtime caching is in play, because runtime cache-first grabs hashed assets on first load anyway.

Workbox earns its keep in the separate indiee finisher-template plan, where the goal is a precache manifest that auto-expands as a forker adds post types across many sites. That is a template-reuse problem JEDEE — a single site — doesn't have. Keep Workbox in the pocket for indiee; it buys almost nothing here.

5. The offline page

src/pages/offline.md (permalink /offline/) renders through the normal base.njk layout and is precached on install. It is now strictly the last resort: the network-first branch reaches it only when you are offline and the requested URL was never visited (so it isn't in the cache). Any page you have opened before is served from cache instead.

6. Open / next

  • stale-while-revalidate is the natural addition if you ever want instant loads and background freshness on the same resource. The place it would help is non-versioned third-party assets. Not wired today.
  • No install-prompt UX (the beforeinstallprompt button / iOS "Add to Home Screen" hint). The site is fully usable without it; deferred.
  • No per-entry cache expiry — relies on the per-build cache reset (§3).
