Micropub endpoint

Brainstormed 30 May 2026 · built (v1) 2026-05-31 · v1 = create-only, text posts · ports the indiee ROADMAP M11 decision onto JEDEE-as-it-is · companion to the micropub skill

Micropub is the W3C-recommended way to create posts on your own site over HTTP: any Micropub client can talk to any Micropub server. This page is the design for JEDEE's Micropub server — a single Netlify Function that turns an incoming h-entry into a shape-correct .md committed to the repo. The goal is post-from-anywhere: publish a note, reply, like, bookmark, RSVP — or a film/book/album via Sparkles' editors — from a phone, with the laptop off.

Status: built (v1), 2026-05-31 (branch feat/micropub-endpoint; not yet pushed). The Function (netlify/functions/micropub.js), its deps, the [functions] esbuild block, the meta.indieweb block, and the three discovery links (micropub/authorization_endpoint/token_endpoint) are all wired; before a real client can authenticate it still needs the Netlify env vars set + the domain move (§10). This design was recovered, not invented: the archived indiee-phase-1 template already settled the architecture in its ROADMAP milestone M11 ("Default Micropub endpoint → serverless"). What's new here is reconciling M11 against the three places JEDEE diverged from that template (§5) and the 2026 IndieAuth landscape (§4). The build plan is both: capture this as the portable micropub skill, then build the endpoint.

1. What it buys JEDEE — and how it sits next to the Web Clipper

JEDEE already has a CMS for browser-shaped posts: the Obsidian Web Clipper. Micropub does not replace it — the two are complementary authoring paths over the same .md content layer:

 Web ClipperMicropub endpoint
ShapeBrowser extension → Obsidian vaultHTTP endpoint → GitHub commit
Best forDesktop, rich-source clips (a book / film / album / page you're looking at)Quick posts from anywhere; phone; standard IndieWeb clients
Needs runningThe browser + Obsidian, locallyNothing local — the Function is always-on
Writes viaObsidian (local file)GitHub Contents API (remote commit → Netlify rebuild)
Authoring typesreading, watching, jam, bookmark, reply, like, notes, …note, reply, like, bookmark, rsvp + Sparkles' watch / read / jam

Both paths, same content layer. A Clipper clip and a Micropub post land as the same kind of .md in the same src/posts/<type>/ folder, governed by the same per-type frontmatter and µf2 conventions. Micropub is the "I'm not at my desk" path; the Clipper is the "I'm reading this in a browser tab" path.

2. Architecture & data flow

One Netlify Function (JEDEE's first), mounted at /api/micropub:

Micropub client (Sparkles / Quill / iA Writer / Indigenous)
   │  POST h-entry  (form-encoded or JSON) + Authorization: Bearer <token>
   ▼
Netlify Function  /api/micropub
   │  1. verify token against the token endpoint  (§4)
   │  2. route h-entry → post type by property presence  (§6)
   │  3. map properties → JEDEE frontmatter + title-only filename  (§5)
   │  4. PUT the .md via the GitHub Contents API
   ▼
GitHub commit → Netlify auto-rebuild → post is live

No tunnel, no MongoDB, no long-running server. The Function is stateless; the repo is the database; Netlify's build is the deploy. This is the M11 model: "the function writes posts to the repo via the GitHub API; the resulting commit triggers the host's auto-rebuild."

3. The engine — @benjifs/micropub, not the wrapper

The obvious starting point, benjifs/serverless-micropub, is a thin ~6-file Netlify deployment wrapper — its function files literally just call micropub.micropubHandler(request). The real logic is two npm packages:

PackageRoleHealth (checked 30 May 2026)
@benjifs/micropubThe engine — a Request→Response handler doing auth, routing, frontmatter, CRUD, media, and the Micropub query surface (q=config…)Maintained through Dec 2025, has a test suite, MIT, 0 open issues, run in production by the author
@benjifs/github-storeStorage backend — PUT/GET/DELETE against the GitHub Contents API (Base64, custom branch + committer)MIT, host-agnostic

So "is serverless-micropub maintained?" really means "is @benjifs/micropub maintained?" — and it is. Netlify Functions are the reference target (the wrapper ships netlify.toml with the esbuild bundler, a /* → /.netlify/functions/:splat redirect, and a "Deploy to Netlify" button). The engine itself is host-agnostic, so the same code runs on Cloudflare Workers / Vercel.

Decision: vendor-but-patch. Depend on @benjifs/micropub + @benjifs/github-store and write a thin Netlify Function around them (à la the wrapper), then override the three JEDEE-specific output conventions in §5. The engine's auth, property-routing, GitHub backend, and CRUD are exactly JEDEE's design and are tested — writing them from scratch (pure custom) throws that away for no gain; using it as-is (pure vendor) can't produce JEDEE's title-only filenames or camelCase keys. Alternatives weighed and rejected for v1: Indiekit (a full long-running Node server — more than "one Function," though it bundles its own token endpoint) and voxpelli/webpage-micropub-to-github (a standalone web service, Jekyll-shaped output).

4. Auth — fully hosted IndieAuth, zero self-hosted server

Micropub mandates a bearer token. JEDEE will not run an auth server; it delegates entirely to hosted IndieAuth services and the Function only verifies the token (it's a pure resource server). Landscape, verified alive May 2026:

ServiceRoleUse
indieauth.com/authauthorization_endpoint — authenticates you (via rel=me) and authorizes the clientAlive; officially deprecating ("will eventually be replaced by two new services") but works today
tokens.indieauth.com/tokentoken_endpoint — issues and verifies tokens; "no registration required"Alive; the drop-in a static site points at without self-hosting
indielogin.comAuthentication only (domain / GitHub / email)Not a token endpoint — can't authorize Micropub writes on its own

How the engine verifies a token (from @benjifs/micropub src/auth.js): it fetches TOKEN_ENDPOINT with Accept: application/json and Authorization: Bearer <token>, then authorizes iff the returned me equals the configured ME. Token is read from the header or an access_token body param (rejected if both are present); scope is checked per-action.

# Function environment
ME             = https://johanedlund.se/
TOKEN_ENDPOINT = https://tokens.indieauth.com/token
GITHUB_TOKEN   = <a token with contents:write on the repo>   # §9
GITHUB_USER    = pjedlund
GITHUB_REPO    = jedee

The authorization_endpoint/token_endpoint split still exists in metadata but has converged in practice — they're almost always one system now, and the inter-server protocol text was dropped from the spec. A resource server only needs to take the bearer token, hand it to the token endpoint, get back me/scope, and check me. The legacy GET-with-Bearer → JSON shape (what tokens.indieauth.com serves and what the engine uses) and the newer POST token-introspection both exist; the engine uses the former, which is fine.

5. The three JEDEE patch points

This is why "patch" and not "use as-is." The engine's defaults are sensible but collide with three JEDEE conventions it exposes no hook for. Each is a small, contained override.

#Engine defaultJEDEE conventionFix
1generateSlug() prepends a unix-timestamp prefix for note-type posts (1733436000-my-post.md)Title-only filenames so Obsidian [[wikilinks]] resolve (the nice-permalinks pattern)Patch generateSlug / force the no-prefix branch
2slugify lowercases + kebab-cases the filenameTitle-Case filenames (Anna Karenina.md); permalinks are kebabbed separately via {{ page.fileSlug | slugify }}Preserve Title Case for the filename; let the permalink filter do the kebab
3toFrontmatter emits hyphenated mf2 keys (bookmark-of, in-reply-to)camelCase keys (bookmarkOf, inReplyTo) with the kebab class on the <a> in the layoutExtend translateProps with the kebab→camelCase map (§6)

As built (2026-05-31, engine v2.0.1). The engine exposes no source-level hooks for generateSlug or the translateProps dictionary — only constructor-option seams. So the patches were applied through those instead (cleaner — no node_modules edits): patch 1 via formatSlug (maps engine-type→folder and strips the leading ^\d+- timestamp); patch 3 via a store wrapper that parses the engine's frontmatter (gray-matter), renames the kebab target keys, drops type/client_id/mp-*, merges tags, then re-stringifies before the commit. Patch 2 (Obsidian Title-Case filenames) was initially deferred but is now implemented (2026-06-02) in the store's resolveFilename: any post carrying a title is renamed to <title>.md verbatim (Title Case, spaces and commas kept; only Obsidian-illegal chars stripped) so [[wikilinks]] resolve, while the permalink still slugifies page.fileSlug so the URL stays clean (Project Hail Mary.md → /watching/project-hail-mary/). A client mp-slug no longer hijacks the filename — on a titled post it is written as a slug frontmatter field that drives the URL instead (the titled-type permalinks honor {{ (slug or page.fileSlug) | slugify }}, articles {{ (slug or title) | slugify }}), so the file keeps its Obsidian title and the custom slug sets a clean URL (added 2026-06-02). The earlier “non-goal” reasoning held for notes/likes but broke for watch/read/jam — those are film/book/album [[wikilink]] targets exactly like clipped ones. All of it lives in netlify/functions/micropub.js (unit-tested in micropub.test.js).

Terminology collision — Micropub category ≠ JEDEE category. In Micropub, category is the post's user tags. In JEDEE, category is the post type that drives collections (byCategory() in src/_config/collections.js), and it is inherited from the folder's directory-data file (src/posts/<type>/<type>.json), never written per-post. These must not be confused. The engine's default translateProps already maps Micropub category → tags (plus name → title, published → date) — which is exactly right: it feeds user tags into JEDEE's tags and leaves JEDEE's category alone. Consequence: the endpoint routes a post purely by choosing the destination folder; the post type (category) then falls out of the directory cascade for free.

Open wrinkle — title-less posts. JEDEE's title-only filename convention assumes a title. Notes and likes have none (a Micropub like sends only like-of: <url>). The Web Clipper sidesteps this by deriving a title from the target page (the live clips likes/Liked Make Free Stuff.md, replies/Make Free Stuff.md got their names that way), but a Micropub client typically sends only the URL. So the endpoint needs a filename strategy for title-less posts — derive a slug from the first words of content, from the target URL, or fall back to a timestamp. Decide at build (§9).

5a. status / visibility / slug vocabulary (added 2026-06-01)

Sparkles' note composer exposes slug · status · visibility (its Advanced section), per the Micropub-extensions de-facto standard. JEDEE models only draft natively. The principle is the same as the three patch points above: keep JEDEE's native vocabulary, translate the Micropub-extension fields at the endpoint boundary (exactly as post-status already was) — so all three authoring paths (hand-written · Web Clipper · Micropub) share one documented frontmatter contract per type.

AxisMicropub inputJEDEE frontmatter (the contract)Where interpreted
statuspost-status: draftdraft: trueendpoint (unchanged)
post-status: published (or absent)(omitted — publishes)endpoint (unchanged)
visibilityvisibility: unlistedvisibility: unlisted (native key)endpoint → build (drafts.js)
visibility: privatedraft: trueendpoint (reuse draft)
visibility: public (absent / other)(dropped — no stray key)endpoint
slugmp-slug: xfilename xengine honors; store re-slug guarded off

Unlisted = native key, central interpretation. visibility: unlisted is kept verbatim and interpreted in one place — src/_config/plugins/drafts.js, mirroring how it already interprets draft. It sets eleventyExcludeFromCollections (so the post drops from every archive, every per-type feed, the firehose, and the sitemap — those all read collections.*, which honor the exclusion) plus a new per-post noindex, while the permalink still resolves. Unlike a draft, it is a permanent property — never build-mode-gated. The noindex is emitted by a flag-driven head/meta-info.njk ({% if meta.noindexSite or noindex %}); the new meta.noindexSite flag also replaces the hard-coded soft-launch tag, so the 1.0.0 go-live step becomes "set meta.noindexSite = false" (an improvement on deleting lines) and unlisted posts keep their noindex after launch.

"Private" is a documented limitation, not encryption. A statically-built public site has no true private state. visibility: private collapses to the existing draft mechanism (no public output) — "private" here means unpublished, not authenticated-private. The contract reserves visibility for unlisted; private is expressed as draft: true on every authoring path. A client shouldn't be told a post is private when the platform can't honor it, so this limitation is documented rather than silently mapped.

Re-slug guard (refines the title-less strategy above). The engine's generateSlug (v2.0.1, src/content.js) already gives a client mp-slug top priority, so it reaches the filename for titled and title-less posts. The store's title-less re-slug therefore fires only when the slug is a bare engine timestamp (/^\d+$/ — the engine had nothing to name from), never when the user set mp-slug or a cite-derived slug exists (star-wars-1977, which doesn't match ^\d+$). The earlier condition was the too-broad !data.title, which silently clobbered a note's mp-slug — the most common Micropub type. The slug decision is a pure helper, resolveFilename(filename, data, content) — which also produces the titled-post Title-Case filename (patch 2) — unit-tested without GitHub I/O.

Watch / Read / Jam come for free. The engine has native watch-of/read-of/listen-of types, so Sparkles' Movie / Book / Listen editors route correctly with no custom plugin — an improvement on the old indiee design, which needed inline Indiekit discovery: config for Watch/Read. Confirmed against the layouts (2026-05-31): the targets read url / link / source (the clipper-origin keys), not watchOf/readOf/listenOf — the Function maps the engine's watch-of/read-of/listen-of to those. The 15-type list and the byCategory() mechanism live in src/_config/collections.js.

…but not shape-free — the cite must be destructured (2026-06-02). Sparkles' Movie/Book/Listen editors (src/js/Editors/MediaEditor.js) send the media's identity as a nested h-cite — name/photo/url/published/author/content — with no top-level name, plus the poster again top-level as featured. So the engine's translateProps yields no title, and a naive flatten() of the cite keeps only its url — dropping the film's title and poster (the first posted film, project-hail-mary-2026.md, landed titleless with a featured key the cover-reading layout ignored). The store now destructures the cite: name→title, photo→cover (top-level featured as fallback), published→year, author→author, content→plot; title then drives the Title-Case filename (patch 2). The identity key (url/link/source) remains the cite's url.

6a. The per-type frontmatter contract — all 15 types (added 2026-06-01)

The routing table (§6) shows how an incoming h-entry picks a folder. This is the other half: once it lands, what frontmatter must each type carry? One documented contract per type, honored identically by all three authoring paths — hand-written, Web Clipper, Micropub. The key insight is that the contract is mostly shared: every type carries the same spine; only the identity key and a handful of type-specific fields vary.

The shared spine — identical across all 15 types, so it's stated once here, not per-row:

title (added 2026-06-03)Every post carries one. A title-less post would otherwise go blank in the page <title>, og:title + the OG-image path, the Atom/JSON feed entry <title>, the notes card headline, and the hidden h-entry p-name. The three tiers — and the decision on the non-routable types (2026-06-01). Tier A (10 types) is the live Micropub surface: text or a target-URL, postable from any client, and exactly the set advertised in q=config (§8a) so Sparkles/Quill show the right editors. Tier B is photo alone: TYPE_DIR carries a forward-wired photo entry, but it is deliberately absent from q=config (so no client offers it) and its layout reads a nested local photo.* asset — a Micropub flat photo: <url> wouldn't render. Photo therefore joins the deferred media endpoint milestone, not the v1 text path. Tier C (audio, video, event, recipe) has no Micropub route and is documented as out of scope: audio/video need binary uploads (the same media-endpoint milestone); event and recipe have no native engine PTD type and no standard client editor (a recipe is a kepano-shape body the Web Clipper builds, an event is a hand-authored h-event). All five still honor the same spine — a hand-authored or clipped audio post gets the same draft/visibility/tags/date treatment; only the authoring path differs. Inventing routing rules for them was weighed and rejected for v1 (no client speaks those types, and the media ones are blocked on storage anyway).

8. Scope — v1 and what's deferred

v1 = lean, create-only, text posts. Smallest surface that satisfies "post from mobile" + Sparkles, and it sidesteps the fiddliest part (read-modify-commit for edits on a git-backed site).

8a. Micropub-extensions conformance (added 2026-06-01)

"Conform to the clients" concretely means the Micropub-extensions de-facto standard — the features clients implement beyond the core spec. The extensions go through three stages (proposed → stable → official; there are no official ones yet). This is where each maps onto the endpoint as built:

ExtensionKind / stageEndpoint status
Slug (mp-slug)property · stable✓ engine honors; the store's re-slug is guarded to a bare timestamp so it never clobbers a client slug (§5a)
Post Status (post-status)property · stable✓ draft → draft: true; published/absent → publishes (§5a)
Visibility (visibility)property · stable✓ unlisted kept native; private → draft; public/other dropped (§5a)
Destination (mp-destination)server command · stableN/A — single-site endpoint; no destinations advertised
Supported Vocabulary (q=config → post-types[])query · stable✓ done — advertises the 10 Tier-A types (§6a) so a client (Sparkles/Quill) shows the right editors and hides the rest. This is reverse Post Type Discovery.
Category/Tag List (q=category)query · stable✗ deferred — a clean follow-on (return the existing user-tag list for client autocomplete)
Post List / Limit / Offset (q=source family)query · stable✗ deferred — bundled with q=source + update/delete (§8)
Location Visibility · Audience · Standalone Pages (h=page) · Draft Scopeproposed (not stable)✗ deferred — known; none needed by v1's post kinds

What's already shipped vs. the real follow-ons. The three stable creation-time properties (mp-slug, post-status, visibility) and the stable Supported-Vocabulary query are all done — that is the whole "make clients conform to this site" set. The earlier handoff floated Supported Vocabulary as something to propose; it is in fact wired in the Function's config.post-types (the empty media-endpoint and syndicate-to sit alongside it, advertised-but-empty). The genuine remaining levers are q=category (tag autocomplete) and a real q=syndicate-to target list — the latter would surface the existing syndication: field as POSSE targets (see the indieweb skill) — both deferred to the same v1.1 that brings q=source/update/delete. The proposed-stage extensions stay parked until a post kind needs them (e.g. private-audience posts would want Audience + the not-yet-real private state of §5a).

9. Build-phase open decisions

These don't block capturing the skill; they block the build. All five resolved at the Phase-2 build (2026-05-31) — see annotations.

  • GitHub token mechanism. A fine-grained PAT (contents:write on pjedlund/jedee) stored in Netlify env, vs. a GitHub App. PAT is simplest for one repo; an App is tidier if this ever becomes a template others fork. Lean toward PAT for v1. → Resolved: PAT (Netlify env GITHUB_TOKEN, with GITHUB_USER/GITHUB_REPO/ME; optional GITHUB_BRANCH).
  • Commit target & rebuild. Commit straight to main (immediate publish) vs. a branch (review first). For a personal site, straight to main matches the "post and it's live" intent. → Resolved: main (no GITHUB_BRANCH set → the store commits to the repo default).
  • Title-less filename strategy for note / like (§5 wrinkle): content-slug vs. target-URL slug vs. timestamp fallback. → Resolved (Johan): content-slug → target-URL → timestamp, done in the store wrapper with a Location-header rewrite so the client's "view post" link stays correct. (Edge: a content-slug collision fails the commit with a 400 rather than overwriting — rare for a personal note stream; reword to retry.)
  • Exact frontmatter key for watch / read / jam targets (§6 ⚠ rows) — confirm against the layouts. → Resolved: url / link / source (the Function maps the engine's watch-of/read-of/listen-of).
  • Function bundling on JEDEE's Netlify setup — add a [functions] block + esbuild to netlify.toml (none today); confirm Node version parity with .nvmrc (22). → Resolved: done — [functions] node_bundler = "esbuild" added; an esbuild bundle of the Function + its deps was verified on Node 22 (~599 kb). Routed via the Function's own export const config = { path: "/api/micropub" } (Functions v2), so no redirect was needed.

10. Sequencing — coupled to the domain move

Buildable now, usable only after johanedlund.se is live. IndieAuth authenticates you by following rel=me links from your me URL and back (bidirectional). JEDEE is currently noindex on jedee.netlify.app, while rel=me and the webmention endpoint already point at johanedlund.se. So a Micropub client authenticating against https://johanedlund.se/ needs that domain serving the real site with matching rel=me back-links. The endpoint can be written and unit-tested against the token endpoint before then, but real client auth presupposes the domain switch (an open question in TODO.md).

11. Host portability — not tied to Netlify

Netlify is only the function runtime + static host here; nothing proprietary is baked in. The three load-bearing pieces are all host-agnostic: the engine (@benjifs/micropub) is a plain Web Request → Response handler — the same shape Cloudflare Workers, Vercel, Deno, and Bun use; storage (@benjifs/github-store) only talks to the GitHub Contents API over fetch (the repo is the database — the host never sees the posts); and auth is fully hosted IndieAuth (§4), external to any host. The Function imports zero @netlify/* packages — only standard Web APIs (Request/Response/Headers/URL) plus process.env.

Migration cost ≈ a 10–15-line glue rewrite — the wrapper, the routing, and env access. The logic that makes a posted entry shape-correct (the formatSlug folder-map, the store wrapper's frontmatter rewrite, the title-less slug) is plain JS and moves untouched; the posts still land in the same repo and render identically. Only what rebuilds the static site on commit changes — and Netlify, Cloudflare Pages, and Vercel all do build-on-push. To make a future move trivial, extract the engine config + the store wrapper into a host-neutral module and keep only the export/routing line per host.

One Node-runtime caveat. The deferred media path (parseBody's multipart branch) uses Node streams (node:stream + busboy), so it assumes a Node runtime. The v1 create path (JSON / form-urlencoded) uses only req.json() / req.formData() — pure Web standard — so what's built is fully portable; only the not-yet-wired media upload would need a tweak on a non-Node edge runtime (e.g. Cloudflare Workers).
