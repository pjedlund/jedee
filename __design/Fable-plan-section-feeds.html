Feeds for every section: events, likes, reposts — and untangling audio/video

You decided this back in May (TODO §5) and it never got built: every section should offer the standard Atom + JSON feed pair like reading and jams already do. Three sections have none at all, and audio/videos have a podcast feed sitting on the address a regular feed should own. Each new feed is a ten-line file copied from an existing one.

What gets added

SectionNew feeds

Audio/audio/feed.xml + /audio/feed.json (regular), podcast feed moves to /audio/podcast.xml
Videossame pattern: regular pair + /videos/podcast.xml

The one decision, and how this plan settles it

Audio/video had an address clash you left open ("no preference"): the regular feed and the podcast feed both want feed.xml. This plan picks: the regular feed gets the standard address; the podcast feed moves to podcast.xml. Reasoning: feed.xml then means the same thing in all sixteen sections — and moving a public address is free right now, because the site is still in soft-launch and nobody is subscribed. That's also why this should run before the 1.0.0 launch; afterward the move would break real subscribers. If you'd rather keep the podcast where it is, say so before this runs — it's the only judgment call in the plan.

Deliberate non-changes (so nobody "helpfully" adds them)

  • No feed links in the page <head> — only the site-wide firehose is auto-discovered, consistent with every existing section.
  • No feed links on the section pages, and no feeds index page — separate idea, not this job.
  • No JSON twin for the podcast feeds — podcast apps only read the XML kind.
  • The shared feed templates themselves stay untouched; only thin per-section wrapper files are added.

Gotchas already scouted

  • Every feed file needs the two "stay out of collections and the sitemap" front-matter lines — forgetting them leaks feed URLs into listings.
  • The feed's self-address is written twice (address + a variable inside) and must match, or validators complain.
  • Likes and reposts may have zero published posts today — an empty feed is valid and expected, and gets verified rather than assumed.
  • The audio/video sample posts are drafts, so a normal build gives empty feeds there too — verification uses a drafts-included build and a normal one.

Done means

  • All ten new/changed feed addresses build and pass an XML/JSON validity check.
  • None of them appear in the sitemap or any listing.
